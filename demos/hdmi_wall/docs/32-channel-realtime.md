# 为什么部分 32 路配置抽帧后没有画面

[仓库首页](../../../README.md) / [HDMI 文档导航](../README.md#文档导航) / [实测索引](results.md)

本页解释早期配置失败，不能据此认定当前所有 32 路 latest 都失败。新配置和验证范围见 [数据总览](current-data.md)。

本文解释早期 32 路无检测画面的机制与原始证据。后续已加入首帧预取等优化，普通双卡各 32 路 latest 的当前验证见 [实测索引](results.md)；保留本报告不表示当前必须改用 all。

**32 路不是程序禁止抽帧的路数。问题是当前实现先完整解码，再选择最新帧，并对超过 250 ms 的候选帧执行淘汰。** 在某些输入、设备链路和主机负载组合下，部分通道不能持续及时解码，送检时已经超龄，因而可能长期没有检测结果。要区分“支持配置 32 路”和“当前硬件条件下 32 路全部实时出结果”。

## 当前抽帧发生在哪里

处理顺序是：读取压缩视频 → 解码原始帧 → 检查帧年龄 → 替换待检测槽中的旧帧 → 按检测上限选取最新帧 → 推理 → 同帧画面和检测框显示。

`--infer-fps 5` 只限制每路检测启动频率；25 FPS 的输入仍需要每秒解码 25 帧。每卡 32 路 1080p25 对应每秒 800 张解码帧，不能因为只检测 5 FPS 就按每卡 160 张解码帧计算。多卡切页也不会暂停未显示设备，后台负载仍然存在。

本地视频的年龄从该帧计划读取的时刻起算。在 `latest` 默认的 `--max-frame-age-ms 250` 下，解码后发布候选帧、检测取帧时都会检查年龄。若帧已超龄，宁可丢弃也不把旧画面作为当前结果送检。待检测槽只有一张图，解决了应用层检测排队，但不能消除解码之前或解码过程中的落后。

## 实测依据

旧测试使用单卡设备 1、YOLOv8n / score gate 开启，以及公路 1080p25 视频。32 路 `latest / 8 FPS` 实测总解码约 **746 FPS**，低于输入需要的 **800 FPS**，19 路始终没有检测结果。完整条件见[原上板报告](realtime-board-validation.md)。

2026-09-09 重刷后，另用两卡各 32 路、官方约 24 FPS 视频、n / gate on、latest / 5 FPS / 年龄 250 ms，正式运行 60 秒：

| 指标 | 设备 0 | 设备 1 |
|---|---:|---:|
| PCIe 链路 | Gen2 ×1 | Gen3 ×2 |
| 总解码 FPS | 768.85 | 773.70 |
| 总检测完成 FPS | 21.95 | 138.55 |
| 每路检测完成 FPS 范围 | 0–2.00 | 3.77–4.80 |
| 全程没有检测结果的通道 | 3 / 32 | 0 / 32 |
| 超龄丢弃帧数 | 41,159 | 8,379 |

其中设备 0 的 stream_00 解码了 **1,429 帧，全部因超龄被丢弃，检测完成 0 帧**。这直接说明了为什么界面会等待检测结果。它也说明平均解码 FPS 接近输入需求并不足以判断实时性：平均计数不保证每帧都按时完成，也不保证启动或运行中产生的落后已被追回。

两张卡的链路宽度和速率不同，应优先核查设备 0 的链路和传输开销；本次对照没有单独隔离 PCIe、启动过程与主机调度的影响，不能将 PCIe 宣称为唯一原因。新旧测试输入也不同，不能直接将两组解码 FPS 当作同条件性能提升。

## 为什么改成逐帧后能显示

`--policy all` 按顺序解码并完成检测，关闭上述抽帧与送检年龄淘汰。处理慢时仍继续输出旧帧，因此能够保持全部通道有画面，但源时间延迟会累积。

双卡各 32 路、同一官方输入、n / gate on 的 90 秒逐帧测试中，64 路全部有结果：设备 0 每路约 **8.49–8.71 FPS**，设备 1 每路约 **9.87–10.10 FPS**；两卡最差一路结果源帧年龄 P95 分别达到 **57.75 秒**和 **52.50 秒**。因此，当时的 32 路展示暂用逐帧模式完成多路显示验证；不将其作为低延时实时验收。运行命令见[多设备分页视频墙](multi-device.md#每卡-32-路优先完整显示的逐帧配置)。

`STALE` 表示当前画面年龄超过 2 秒。它提示屏幕显示的是较旧的内容；检测框仍对应显示的那一帧。

## 要让 32 路实时，需要继续解决什么

该阶段已验证的低延时配置是**单独运行设备 1，24 路 1080p25 输入，每路抽帧检测约 5 FPS**，使用 YOLOv8n INT8 batch 1、score gate on。之前的 60 秒测试中，每路检测完成 4.97–5.00 FPS，各路每个正式 10 秒窗口都有结果；最差一路源帧年龄 P95 为 116 ms，所有完成结果最大为 293 ms。输入 25 FPS 不等于逐帧检测 25 FPS，源帧年龄也不是摄像头到 HDMI 的端到端延迟。这是重刷前设备 1 单卡、重复同一本地公路视频的短测结果，不能直接推广到设备 0、双卡同时各 24 路或真实相机，完整条件见[原上板报告](realtime-board-validation.md)。

继续优化时，先区分“解码追不上源”和“检测来不及”，按以下顺序验证：

1. **检测较慢、解码仍能及时推进**：保持单槽 `latest`，降低 `--infer-fps`，给解码、预处理和主机调度留余量。24 路从检测上限 8 降到 5 FPS 的测试已展示了这条路径的效果，但不能据此保证 32 路达标。
2. **解码已落后源时间**：继续降低检测频率未必足够。若业务允许，降低视频源本身的帧率或分辨率；仅在解码后少送几帧检测，仍然需要解码原来的全部输入。若必须保持每卡 32 路 1080p25，则需要继续测量并优化解码、传输和主机调度，首先对照两张卡的 PCIe 链路差异。
3. **短暂卡顿之后始终无法追回**：需要真正跳转到新的可解码位置或对直播解码器做恢复，才能清除已落后的源数据；这是待实现并验证的能力。不能在 H.264/H.265 中随意跳过压缩帧而不考虑参考帧依赖，也不能通过重置年龄时钟把旧画面算作实时。

每项调整都应逐路检查检测覆盖、连续无结果时长、源帧年龄及随运行时间的变化。仅关闭 250 ms 门槛或隐藏 `STALE` 可以改变送检或显示行为，不能解决累积延时，也不能保证长期不出现过期画面。
