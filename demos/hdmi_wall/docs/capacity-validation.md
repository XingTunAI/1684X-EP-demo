# PCIe 回传与 TPU 满载解码测试

[仓库首页](../../../README.md) / [HDMI 文档导航](../README.md#文档导航) / [实测索引](results.md)

本页为逐卡隔离诊断；若要查看双卡真实视频推理和回传开关，请看 [数据总览](current-data.md)。

本次测试对应两个问题：PCIe 2.0 ×1 是否限制 TPU 的实际使用，以及 TPU 计算满载时解码吞吐会下降多少。采用独立诊断入口隔离传输、模型计算和解码；没有启动 HDMI、VPP 预处理、NMS 或预览，所以结果不等同于完整视频墙的能力。

## 条件与判定

2026-09-10，RK3588、两张 BM1684X，逐卡测量，另一张卡保持空闲。device 0 为 PCIe 2.0 ×1（5 GT/s ×1），device 1 为 PCIe 3.0 ×2（8 GT/s ×2）。驱动为本板 0.5.1-LTS-rk3588fix2，SOPHON FFmpeg 0.14.0。开始前通过正常停止入口结束了运行中的双卡 stress，并保留其记录 `20260910T023514Z-9a7e98ba`。

模型为官方 YOLOv8s INT8 batch 1，输入 / 输出边界为 FP32。计算探针预先准备驻留输入、输出缓冲，使用全零输入执行真实模型；开始前核对参考输出。`compute` 不逐次回传输出，`copy` 重复回读已生成输出，`compute-copy` 每次计算、同步并完整回读 2,822,400 字节。它们的循环数不是视频检测 FPS。

解码输入为官方 1920×1080、H.264、24 FPS 的 600 秒无损循环素材；使用 SOPHON `h264_bm`、`-zero_copy 1 -output_format 0`，输出到 null。不限速组去掉源节流，按 8、16、32 路增加并发，避免输入最多供应 768 FPS 导致测不到吞吐平台。纯解码 / 带负载组保留相同解码参数。

负载组启动 2 个独立 compute 进程，不把解码帧送入模型；负载持续覆盖整个解码正式区间。TPU 只统计该区间内的查询，至少 3 个有效采样、无失败采样，且至少 90% 的样本达到 95%，才标记本组满足高负载条件。这是采样判定，不保证任意瞬间都为 100%。

## PCIe 与模型计算的隔离结果

下面采用 2 个并发进程，每种模式预热 3 秒、正式 10 秒。各组正式区间均有 10 个有效 TPU 采样，无采样失败；固定输入首末输出核对通过。

| 模式 | Gen2 ×1 循环/秒 | Gen2 ×1 TPU 平均 | Gen3 ×2 循环/秒 | Gen3 ×2 TPU 平均 |
|---|---:|---:|---:|---:|
| compute：驻留模型计算 | 371.83 | 100% | 371.36 | 100% |
| copy：仅完整输出回读 | 104.35 | 0% | 208.35 | 0% |
| compute-copy：计算后完整输出回读 | 77.80 | 20.60% | 143.27 | 41.60% |

两卡的纯模型计算速率相近，且都能达到采样 100%；Gen2 ×1 没有阻止这类驻留计算使用 TPU。加入完整输出回读后，两条链路都会使这种串行计算 / 回读循环明显减速，Gen2 ×1 更明显。证据指向回传路径及调用等待限制后续推理提交，不能把较低 TPU 利用率解释为 TPU 本身算力不足。

SDK CDMA 工具每次传输 16 MiB，每方向内部循环 10 次，外部重复 3 次，数据核对全部成功。下表为 3 次结果均值，统一使用十进制 MB/s：

| 方向 / 计时范围 | Gen2 ×1 | Gen3 ×2 |
|---|---:|---:|
| 主机→设备，应用侧调用计时 sys | 318.86 | 836.77 |
| 设备→主机，应用侧调用计时 sys | 145.70 | 330.00 |
| 主机→设备，SDK profile 计时 real | 384.52 | 1418.33 |
| 设备→主机，SDK profile 计时 real | 398.34 | 1449.42 |

`sys` 和 `real` 的计时范围不同，尤其设备→主机的应用侧速度明显低于 SDK profile 速度；因此不能只拿物理接口带宽解释全部调用耗时。另测 256 KiB 和 2,822,400 字节尺寸，原始结果一并保留。原 SDK 工具标签写 MB/s，实际按 MiB/s 计算，本表已换算。

这组结果支持“Gen2 ×1 的实际回传路径更慢，会限制需要频繁完整回读的推理循环”。尚未对同一张卡、固定配置进行链路强制降速或插槽交换 A/B，因此不能把跨卡全部差异严格归因于 PCIe 代际，也不能用它代替 HDMI 中 VPP / 预览竞争的隔离测试。当前视频墙的 score gate 会减少回传量，不能直接套用这里完整回传的 77.80 次/秒。

## 解码扫描结果

每档预热 10 秒、正式 30 秒，窗口 10 秒。不限速扫描结果如下：

| 链路 | 并发解码路数 | 纯解码总 FPS | TPU 满载总解码 FPS | 相对同路数下降 |
|---|---:|---:|---:|---:|
| Gen2 ×1 | 8 | 959.42 | 877.74 | 8.51% |
| Gen2 ×1 | 16 | 958.17 | 877.74 | 8.39% |
| Gen2 ×1 | 32 | 918.50 | 862.55 | 6.09% |
| Gen3 ×2 | 8 | 969.66 | 881.89 | 9.05% |
| Gen3 ×2 | 16 | 966.92 | 879.34 | 9.06% |
| Gen3 ×2 | 32 | 949.34 | 875.20 | 7.81% |

负载组正式采样全部为 100%，每档 29–30 个有效样本、无采样失败；纯解码组正式采样为 0%。8 路增加到 16 路时，两卡总吞吐已基本不增长；本轮观测平台约为纯解码 958–970 FPS、TPU 满载时 878–882 FPS。以各卡 8 路同条件对照，下降约 8.51% / 9.05%。

32 路不限速时总吞吐略低，各路分配也不均衡：Gen2 ×1 满载组最低逐路 10 秒窗口为 20.41 FPS，Gen3 ×2 为 21.51 FPS。不能用总 FPS 除以 24 或 25，就宣称对应数量的实时通道全部达标。

扫描目录为 `data/results/decode-capacity/20260910_104333_15311`（device 0）和 `20260910_104746_17365`（device 1）。device 0 的 16 路负载组期间有一次素材 SHA256 读取，原始结果保留，独立复测在下节注明；8 路对照与其他档位不受这次读取影响。

## 按源帧率读取与确认测试

以下源节流组只记录性能，不宣称严格 FPS 或端到端延时验收。每组正式 60 秒、窗口 30 秒，TPU 采样满足高负载条件。

| 设备 / 链路 | 路数 | 预热 | 总解码 FPS | 最低逐路窗口 FPS | TPU 平均 |
|---|---:|---:|---:|---:|---:|
| device 0 / Gen2 ×1 | 32 | 90 秒 | 768.11 | 23.69 | 100.00% |
| device 0 / Gen2 ×1 | 36 | 15 秒 | 853.72 | 20.34 | 100.00% |
| device 1 / Gen3 ×2 | 32 | 15 秒 | 768.47 | 23.70 | 99.97% |
| device 1 / Gen3 ×2 | 36 | 15 秒 | 872.59 | 21.60 | 100.00% |

Gen2 ×1 最初只预热 15 秒，32 路两个窗口的总 FPS 为 864.34 / 806.82，平均 835.58，仍在追赶启动期间的源进度；这组不能当作稳定源节流结果。将预热延长到 90 秒后重新测量，整段约 768 FPS，最低逐路窗口约 23.69 FPS。原始短预热结果仍保留。

Gen3 ×2 的 32 路组约 768 FPS，最低逐路窗口约 23.70 FPS。可描述为这套独立模型负载下，32 路本地 1080p24 短测接近每路 24 FPS；本次没有接入真实摄像头，也没有证明输入 / 输出全程无延时。FFmpeg 的进度发布粒度会影响有限窗口读数。

36 路两卡均有慢通道，最低逐路窗口约 20.34 / 21.60 FPS；Gen3 ×2 总量虽高于 36×24=864，也不能掩盖部分通道落后与其他通道追帧。尚未逐一测 33–35 路，因此不能把“已测 32 路接近目标”改写成“精确最大路数就是 32”。

排除素材哈希读取的干扰后，Gen2 ×1 的 16 路满载组独立复测 60 秒，总解码为 **879.41 FPS**，TPU 平均 **100.00%**，有效样本 **59**、失败 **0**；与先前约 878 FPS 的平台相符。

## 可以得出的结论

1. **Gen2 ×1 并未阻止驻留模型计算达到 TPU 100%。** 两卡约 372 次/秒的计算结果相近。需要完整输出回读时，Gen2 ×1 的实际传输 / 调用路径明显限制推理循环吞吐；同卡改链路的严格因果对照仍未完成，不能将全部差异归因于物理线速。
2. **本次独立 TPU 满载下的解码观测平台约 878–882 FPS。** 相比纯解码约 958–970 FPS，匹配条件下降约 8%–9%。这是已测素材、代码路径和并发范围内的结果，不是所有场景通用的芯片额定上限；也不能直接换算成完整 HDMI 检测流水线的最大路数。

本轮传输 / 模型隔离、12 个不限速扫描组、4 个源节流组和 2 个确认组均完成，清理后无测试 worker 残留，当前启动周期内未发现 Oops、FIFO -1 或 API timeout 日志。新工具及诊断单元检查 7 项、解码检查 20 项通过；没有重新启动四小时展示。

## 复现方法

运行前结束其他设备任务，先在仓库根目录执行 `bash tools/diagnostics/build.sh`。传输与模型隔离分别使用：

```bash
python3 tools/diagnostics/run_pcie_bandwidth.py \
  --device 0 --app /opt/sophon/libsophon-current/bin/test_cdma_perf
python3 tools/diagnostics/run_inference_diagnostics.py \
  --device 0 --steps 1,2 --warmup 3 --duration 10
```

确认 `bm-smi` 可通过 PATH 调用，或将其 SDK bin 目录加入本次进程的 PATH，以保存有效采样。解码对照使用：

```bash
python3 tools/diagnostics/run_decode_capacity.py \
  --device 0 --input data/inputs/hdmi_wall_demo_loop_600s.mp4 \
  --steps 8,16,32 --warmup 10 --duration 30 --window 10 \
  --target-fps 24 --throughput
```

设备 0 完成后改为 `--device 1`。参数和结果文件解释见 [诊断入口](../../../tools/diagnostics/README.md#tpu-高负载下的解码吞吐)。不要把传输、推理隔离与解码扫描命令同时运行；只有 capacity 工具内部创建的模型负载与解码应当同时运行。
