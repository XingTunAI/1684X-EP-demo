# 设备 0 的路数、启动与持续输出测试

本页记录 device 0（PCIe Gen2 ×1）单卡运行 YOLOv8s 的负载扫描，区分启动等待、实际检测 FPS 和后续输出连续性。**预算 0 KiB 基准已完成 16 / 20 / 24 / 28 / 30 / 32 路的 60 秒短测及 32 路 300 秒测试。32 路最终全部产生结果，但长测存在启动等待和后续秒级断档，不能称整场稳定实时。**

另在 20 路配置中启用 **64 KiB 小块回传合并预算**，60 秒实测总吞吐从 **241.40 提升到 279.67 FPS**，TPU 利用率采样平均从 **83.02% 提升到 95.66%**，详见[合并实测](#20-路64-kib-小块回传合并)。之后启用[本地解码预取](#32-路本地解码预取改善启动)改善了 32 路启动长空窗；[双卡两种模式并发 120 秒](showcase.md#双卡展示与压测并发实测)中，device 0 的 32 路展示 TPU 平均 84.61%，20 路压测为 97.59%。四小时认证尚未完成。

本页容量表、回传预算及 prime 对照均每次只运行一张卡，双卡结果单列在上述 showcase 报告。设备 1 的 Gen3 ×2 链路、30 路基准和 32 路扩展见[设备 1 优化实测](performance-30.md)，不能直接作为设备 0 或双卡同时运行的容量结论。

## 固定条件

| 项目 | 配置 |

| 本地解码预取 | 历史容量扫描保持 `--prime-local-decoders off`；新增 on 组另列，不改写原始基准 |
| 优化 | 每检测器复用预处理缓冲，视频墙缓存相同提交帧的已缩放小图 |
| 显示 | HDMI 页面更新上限 10 FPS，保留同帧图像与检测框、动态年龄和 `STALE` |
| 测量 | 正式区间前预热 3 秒；各路数正式 60 秒，另有 32 路正式 300 秒，600 秒素材在这些测量中均不遇文件 EOF |

`--infer-fps 0` 取消人为检测限频，仍使用 `latest` 覆盖等待中的旧帧、淘汰超龄帧。源解码仍按约 24 FPS 推进，不能把检测 FPS 当作输入 FPS。TPU 利用率由实际工作与等待共同决定，取消限频无法保证每个瞬间满载。

辅助 score gate bmodel 已在本次板子本地准备，不随 Git 下载。更换模型、关闭辅助模型、更换素材或并行启动另一张卡后，需要重新测量。

## 时间区间与统计口径

源时钟起点是所有通道初始化就绪、开始预热的位置，不包含之前的模型和解码器初始化。对于本页 60 秒运行：

| 区间 | 相对源时钟 | 用途 |
|---|---|---|
| 预热 | 0–3 秒 | 正式计数前的预热 |
| 完整正式区间 | 3–63 秒，共 60 秒 | 保留正式首帧等待、后续断档和全部通道，用于主结果 |
| 启动观察区间 | 0–15 秒 | 单独观察启动过程，包含预热及正式开头 12 秒 |
| 后段子区间 | 15–63 秒，共 48 秒 | 分析器中名为 `steady`，用于区分启动慢与后续持续不足 |

`steady` 是分析区间名称，不表示所有配置已经进入稳定状态。不能用这 48 秒替换完整正式结果，也不能把被排除的正式开头 12 秒等待删掉。

连续性分析以记录的检测完成时间划分区间和计算 FPS；C++ 正式 summary 以记录写入时间计数，边界处可能有少量计数差异。各子区间从自己的起点重新按 10 秒分桶，48 秒子区间包含四个 10 秒桶和一个 8 秒尾桶，尾桶同样检查是否有结果。

“含边界最大间隔”包含区间开始到首个结果、相邻结果之间、最后结果到区间结束的等待。仅比较已完成两帧的“相邻间隔”会漏掉首帧长时间没有结果的问题；无结果通道也必须保留。

32 路长测的完整正式区间为源时钟 **3–303 秒，共 300 秒**；后段子区间为 **15–303 秒，共 288 秒**，同样不能替换正式结果。其后段重新分桶后为 28 个 10 秒桶及一个 8 秒尾桶。

### 后半段 wall 状态观察

另从本组源时钟约第 **137 秒**开始，到约第 **299 秒**结束，以约 1 Hz 读取视频墙状态，共 **162 次 × 32 路**：采样字段中 `stale` 为 0、缺图为 0，观测到的最大 `source_age_ms` 为 **658.55 ms**。对应观测 Unix 时间为 `1788942273.1154795` 至 `1788942434.4674413`。

这证明采样覆盖的后半段 wall 状态已恢复到所有通道有图且未标过期，**不能覆盖更早的启动与断档，也不能推断每两个采样点之间都没有异常**。当前 `status.json` 本身每约 5 秒写一次；162 次读取去重后为 **33 份独立状态快照**，不是 162 次独立的新画面。这里观察的是 worker 写出的 wall 状态字段，仍不是 HDMI 显示器端的延时测量。

完整记录中的早期长间隔与这段后期较好的状态可以同时成立，容量判断需要两者一起保留。

## 20 路：64 KiB 小块回传合并

保持 device 0、20 路、s / gate on / latest / infer 0 / age 250 / auto、600 秒输入和正式 60 秒，将 `--gate-merge-budget-kib` 从 0 改为 64。额外预算允许回传相邻候选行之间的一部分间隔，以减少零散读取调用；CPU 仍只处理原来的候选行，不把额外读到的行当作新增候选。

| 指标 | 预算 0 KiB | 预算 64 KiB |
|---|---:|---:|
| 总检测完成 FPS | 241.4000 | 279.6667 |
| 每路检测完成 FPS 范围 | 11.9167–12.2000 | 13.7833–14.0833 |
| 最差一路完成帧源年龄 P95 | 165.455 ms | 143.862 ms |
| 正式空 10 秒窗口数 | 0 | 0 |
| 正式开始到首帧最长等待 | 0.601257 秒 | 0.642258 秒 |
| 已出结果后的最大相邻间隔 | 0.200469 秒 | 0.150429 秒 |
| 正式 TPU 利用率采样平均，均 59 次采样 | 83.0169% | 95.6610% |
| 每帧候选行读取调用次数均值 | 32.441 | 10.98963 |
| 每帧候选行读取阶段耗时均值 | 36.989175 ms | 7.728289 ms |
| 每帧 gate 回传总字节均值，含 maxima | 58,468.59 | 119,482.44 |

总检测吞吐提高约 **15.85%**，TPU 平均利用率提高约 **12.64 个百分点**。64 KiB 组 TPU 采样 P50 为 **96%**、P95 与最大值均为 **100%**；不低于 90% 的采样为 **57 / 59**。这是已测 20 路单卡配置的改善，不能表述为每次采样或每个瞬间都达到 100%。其预览相邻提交最大间隔估算为 **0.234393 秒**，仍不是屏幕端测量。

64 KiB 组每帧原候选范围平均 **33.285 个**，合并后实际行读取调用平均 **10.990 次**；实际额外行字节平均 **60,435.95**，受每帧 **65,536 字节**预算上限约束。它用更多连续字节换取更少小块读取。读取阶段耗时是 API 调用的墙钟时间；原 `output_copy_ms` 还包含 gate 执行等工作，不能把该汇总字段全称为纯 DMA 时间。

两组性能运行采用抽帧，实际选中的源帧集合可能不同，因此表中的逐帧均值不是一组逐帧配对实验。另进行了预算 0 / 64 的**同帧对照**：192 个共同源帧、2,353 个检测框的数量、类别、分数和坐标完全一致；该组同帧读取调用平均从 **40.406 降到 12.859 次**，总字节从约 **63,947 增到 125,312**。这验证本次素材下候选和结果保持一致，不代替带标注场景的准确率验收。

预算以 KiB 指定，支持 `0..1024`，默认 0 保持既有基准。20 路 64 KiB 的复现命令为：

```bash
cd /userdata/1684X-EP-demo
sudo env DISPLAY=:0 \
  XAUTHORITY=/var/run/lightdm/root/:0 \
  SDL_VIDEODRIVER=x11 \
  PLAYER_LIB_PATH=/usr/lib/aarch64-linux-gnu \
  bash demos/hdmi_wall/benchmark.sh \
  --devices 0 --streams 20 --duration 60 --gate-merge-budget-kib 64
```

当前这项结论限于正式 60 秒、device 0 单独运行 20 路；32 路合并后的吞吐、启动与断档需另看实测，多设备长期展示也需同时加载验证。

展示入口进一步使用 Gen2 ×1 的 128 KiB 预算，并与 Gen3 ×2 的 32 路同时运行；压测则选择 20 路 / 64 KiB。两种模式的结果单独放在[双卡并发实测](showcase.md#双卡展示与压测并发实测)，不混入本页单卡扫描表。

## 复现入口

先完成[资源与环境准备](../../../docs/setup.md)并编译。以下在已确认 Xorg 为 `:0`、LightDM 认证为 `/var/run/lightdm/root/:0` 的板端运行；其他会话参见 [ADB / SSH 显示说明](../README.md#通过-adb-或-ssh-运行到-hdmi)。SSH 普通用户使用 `sudo env`，ADB root 可去掉 `sudo`。

下例复现 device 0 的 24 路、60 秒条件，用于测量，不是最终最大容量推荐：

```bash
cd /userdata/1684X-EP-demo
sudo env DISPLAY=:0 \
  XAUTHORITY=/var/run/lightdm/root/:0 \
  SDL_VIDEODRIVER=x11 \
  PLAYER_LIB_PATH=/usr/lib/aarch64-linux-gnu \
  bash demos/hdmi_wall/benchmark.sh \
  --devices 0 --streams 24 --duration 60
```

下一组改成 `--streams 16`、`20`、`28`、`30` 或 `32`，仍一次只测试 device 0。`benchmark.sh` 自动固定 s / gate on / latest / infer 0 / age 250 / image auto，并准备覆盖运行时长的长素材。小块回传合并预算保持默认 0 KiB，才能与当前表格对应。更长测量用 `--duration 300`；不能在上一组仍运行时叠加新一组。

需要提前停止时，以相同身份执行：

```bash
sudo bash demos/hdmi_wall/benchmark.sh --stop
```

## 后续判定

20 路 64 KiB 已完成短时性能与同帧一致性对照，32 路预取组已改善启动长空窗，双卡 32 + 32 路展示和 20 + 32 路压测均已完成 120 秒测试；四小时结论仍需相应完整测量。历史 32 路预算 0、预取关闭的长测存在断档，这项事实与后续优化结果分别保留。本页不宣布“设备 0 最大只能跑某一路数”，也不将某次利用率峰值当作持续满载结论。

最终路数结论需要同时列出每路检测 FPS、启动首帧等待、持续最大无结果间隔和画面保留年龄，并说明允许的等待或中断条件。TPU 平均、峰值或页面数量均不能单独回答容量是否合适。长素材在测试内避开 EOF，也不代表短片循环恢复或真实 RTSP 摄像头已完成验证。
