# PCIe 2.0 ×1 与 PCIe 3.0 ×2：带宽、路数及 TPU 利用率

[仓库首页](../../../README.md) / [HDMI 文档导航](../README.md#文档导航) / [实测索引](results.md)

本报告的 2026-09-09 双卡并发对照中，**PCIe 2.0 ×1 的 20 路配置接近满载，32 路可以检测和显示，但 TPU 平均降至 84.61%；PCIe 3.0 ×2 在两种模式下均运行 32 路，TPU 平均为 99.42%–100%。** 当前验证的低带宽满载档位是 **20 路**，不能扩写为所有“二十多路”配置都能满载。

以下对比使用已经完成的两组正式 120 秒记录，2026-09-09 重新读取板端原始 summary 与遥测核对。没有为本表重新启动压测，也没有把四小时默认时长当作已通过的验收时长。启动命令见[四小时展示与压测入口](showcase.md#启动与停止)。

## 原因总结

**当前最明显的拖慢发生在图像预处理和预览缩放调用。** Gen2 ×1 从已测 20 路 / 64 KiB 预算档位切换到 32 路 / 128 KiB 档位后，预处理平均耗时由 **12.47 ms 增至 56.58 ms**，预览转换缩放由 **6.52 ms 增至 24.72 ms**；预览回传仅由 1.55 ms 增至 1.76 ms。这些是调用墙钟耗时；预处理按正式完成帧统计，预览阶段只统计其中实际提交预览的帧。详细条件与统计口径见[分阶段计时](#分阶段计时明显变慢的是图像处理调用)。

每路虽然独立解码，但该路业务线程仍按“预处理 → 推理 → 结果回读 → 准备预览 → 下一帧”顺序执行。图像处理调用变慢会延后下一次推理提交；增加到 32 路后，共享资源竞争可能抵消并发收益，这与 TPU 平均利用率从 **97.59% 降至 84.61%** 的现象一致。当前证据支持优先排查这些调用和流水线衔接。

**尚未确定这些调用内部的唯一瓶颈。** VPP 图像处理、设备内存访问以及 SDK／驱动排队仍需隔离验证；不能把现有结果写成“PCIe 2.0 ×1 已经用尽 500 MB/s 带宽”。当前可采用的配置是 Gen2 ×1 **20 路接近满载**，或 **32 路展示、接受较低检测速率**；Gen3 ×2 的两种已测 32 路配置均接近满载。

## 链路速率与理论带宽

板端 sysfs 实际读取为 device 0：`0004:41:00.0`、`5.0 GT/s`、宽度 `1`；device 1：`0001:11:00.0`、`8.0 GT/s`、宽度 `2`。换机应重新读取链路，不能根据设备编号猜规格。

| 项目 | PCIe 2.0 ×1 | PCIe 3.0 ×2 |
|---|---:|---:|
| 每条 lane 原始速率 | 5 GT/s | 8 GT/s |
| lane 数 | 1 | 2 |
| 线路编码 | 8b/10b | 128b/130b |
| 单向编码后理论上限 | **500 MB/s** | **1,969.23 MB/s，约 1.97 GB/s** |
| 相对带宽 | 1 倍 | **约 3.94 倍** |

采用十进制单位：1 MB = 1,000,000 字节。计算分别为 `5×10^9 × 8/10 ÷ 8 × 1` 与 `8×10^9 × 128/130 ÷ 8 × 2` 字节/秒；编码和单向口径依据 [PCI-SIG 官方说明](https://pcisig.com/how-does-pcie-30-8gts-double-pcie-20-5gts-bit-rate)。这是扣除线路编码后的上限，尚未扣除报文、流控及实现开销，**不是本板实测 DMA 吞吐**。PCIe 可双向同时传输，本表不把两个方向相加成单向带宽。

## 当前部署配置的实测对比

共同条件：RK3588 + 两张 BM1684X 同时工作；H.264 / 1920×1080 / 约 24 FPS 的官方本地长素材，各通道独立解码同一个文件；YOLOv8s INT8 batch 1、score gate on、latest、infer FPS 0、送检年龄门槛 250 ms、image auto、prime on、summary。每种模式正式 120 秒，每卡有 59 个正式 TPU 有效采样。

| 链路 / 模式 | 路数 | 合并预算 | 总检测 FPS | 每路检测 FPS | TPU 采样平均 | 最差一路源年龄 P95 |
|---|---:|---:|---:|---:|---:|---:|
| Gen2 ×1 / stress | **20** | 64 KiB | **282.63** | **14.06–14.22** | **97.59%** | **140.12 ms** |
| Gen2 ×1 / showcase | **32** | 128 KiB | **234.16** | **7.17–7.48** | **84.61%** | **258.06 ms** |
| Gen3 ×2 / stress | **32** | 64 KiB | **274.30** | **8.53–8.61** | **100%** | **197.07 ms** |
| Gen3 ×2 / showcase | **32** | 64 KiB | **273.43** | **8.49–8.61** | **99.42%** | **206.12 ms** |

两场运行分别是：`showcase = 20260909T091626Z-91e318ad`，`stress = 20260909T091927Z-d8c6351c`。原始文件位于板端 `data/results/hdmi-wall-multi/<run-id>/device_<id>/summary.json` 与根目录 `telemetry-summary.json`，TPU 取 `formal_measurement.devices`；四份 worker 汇总的 `accounting_complete` 均为 true。更完整的连续性指标见[双卡实测表](showcase.md#双卡展示与压测并发实测)。

在当前两个档位之间，Gen2 ×1 从 20 路变为 32 路，路数增加 **60%**，总检测吞吐反而下降约 **17.15%**，TPU 平均降低 **12.98 个百分点**。同为 32 路的 showcase 中，Gen3 ×2 总检测吞吐比 Gen2 ×1 高约 **16.77%**。带宽上限约 3.94 倍并不意味着模型检测 FPS 也会提高 3.94 倍；模型计算、解码、设备内存及调度等环节共同决定最终吞吐。

这是一组实际部署档位对照。Gen2 ×1 的两种模式同时改变了路数和合并预算，两张卡在 showcase 中的预算也不同；尚未把同一张卡以固定配置分别强制协商两种链路做严格 A/B，不能把全部差异只归因于 PCIe 代际。

## 已记录的回传量与实际总线带宽的区别

从上述四份 worker 汇总重新计算，正式完成帧的 score-gate 结果回读与预览回读量如下。MB/s 是**软件计数的字节总量除以 120 秒**，不是 PCIe 硬件监控或连续大块 DMA 测速。

| 链路 / 模式 / 路数 | 检测结果回读 MB/s | 预览回读 MB/s | 这两项合计 MB/s |
|---|---:|---:|---:|
| Gen2 ×1 / stress / 20 | 33.71 | 15.67 | **49.38** |
| Gen2 ×1 / showcase / 32 | 41.97 | 17.06 | **59.03** |
| Gen3 ×2 / stress / 32 | 30.46 | 23.26 | **53.72** |
| Gen3 ×2 / showcase / 32 | 30.35 | 22.37 | **52.72** |

计算口径：对 `streams[]` 累加 `score_gate_measured.total_d2h_bytes` 和 `preview_readback_bytes_measured`，分别除以 `measured_seconds × 1,000,000`。两项均按预览结束后的正式完成计数时刻归属整帧，边界帧的实际读取可能发生在窗口外；窗口内发生、但未完成或在窗口后才完成的帧不计入。这是成功处理路径上的已记录回读量，字段定义见[指标说明](../../../docs/metrics.md#hdmi-score-gate-与合并回传)。

统计不涵盖输入压缩码流上传、模型加载、控制命令、协议开销及所有其他传输，也不能观察瞬时拥塞。不能把这两项与 500 / 1,969 MB/s 相除后声称得到实际总线占用率，也不能据此证明整个总线没有瓶颈。

当前路径在设备端解码和预处理完整输入，预览只回传每路 **256×144 BGR** 小图；主机再组成一张 **1920×1080、刷新上限 10 FPS** 的页面。因此，不能用 `32 × 1920 × 1080 × 每像素字节 × 输入 FPS` 当作本 demo 的实际 PCIe 回传流量。每路检测约 8.5 FPS 也不表示输出了 32 路独立 1080p 编码视频。

## 为什么增加路数后 TPU 利用率会下降

`latest` 在解码后选择最新帧送检。20 路 1080p24 对应约 **480 解码帧/秒**，32 路对应约 **768 解码帧/秒**；抽掉待推理帧不会同比减少源解码工作。上述正式汇总中，20 路实际合计解码为 480.00 FPS，三组 32 路为 768.03–768.12 FPS，小幅差异来自窗口边界计数。当前优化后的 32 路结果不能沿用旧版本“解码跟不上”的结论。

增加通道会增加解码、设备资源竞争及调度工作。结合下面的回读优化证据，结果与“计算之外的传输、同步及调度使 TPU 出现等待”一致；但当前记录不能确定各项占比或唯一瓶颈，**没有证据证明 Gen2 ×1 已持续用尽 500 MB/s 理论带宽**。

### 分阶段计时：明显变慢的是图像处理调用

进一步读取同一批原始 summary，各阶段按 `sum / count` 合并所有通道后，得到以下调用平均耗时。Gen2 ×1 的 20 路取 stress，两个 32 路取同场 showcase：

| 阶段平均耗时 | Gen2 ×1 / 20 路 | Gen2 ×1 / 32 路 | Gen3 ×2 / 32 路 |
|---|---:|---:|---:|
| 检测预处理 `preprocess_ms` | **12.47 ms** | **56.58 ms** | **16.43 ms** |
| 预览转换缩放 `preview_vpp_ms` | **6.52 ms** | **24.72 ms** | **7.41 ms** |
| 预览回读 `preview_readback_ms` | 1.55 ms | 1.76 ms | 0.90 ms |
| 候选行回读 `score_gate_measured.row_read_ms` | 6.02 ms | 6.61 ms | 2.25 ms |

预处理和候选行回读按正式完成帧统计；两个预览阶段只计其中实际提交预览的帧，不能把未预览帧的零值混入。Gen2 ×1 的 32 路预处理耗时约为 20 路档位的 **4.54 倍**，预览转换缩放约为 **3.79 倍**；回读阶段没有同样幅度的增长。当前最明显的拖慢集中在图像处理调用，不能仅由理论 PCIe 带宽解释。

代码中每路有独立解码线程，但该路业务线程按“取帧 → 预处理 → 主模型推理与同步 → gate 与结果回读 → 按需准备预览 → 下一帧”顺序执行。预览虽发生在本帧检测完成之后，仍会阻塞这一路下一次提交。因此，图像处理和同步调用变慢会延长每路提交周期；更多路数增加的竞争可能抵消并发带来的收益，形成 TPU 无法持续获得可执行工作的空档。这与 32 路时利用率下降的现象一致。

这些都是 SDK 调用墙钟时间。预处理包含缩放、颜色/数值转换及相关等待，预览 VPP 计时也可能包含驱动排队；**尚不能据此断言 VPP 硬件已满、DDR 已满或某个驱动锁就是唯一根因**。要进一步定位，应分别细分 VPP / convert-to / 驱动等待，并在同卡、同路数与同预算下对比预览开关或预览异步化。不同通道的耗时可重叠，不能把它们相加后当成设备独占时间或 TPU 空闲时间。

此前同一 Gen2 ×1、20 路单卡、正式 60 秒的回传合并对照提供了更直接的优化证据：

| 指标 | 合并预算 0 KiB | 合并预算 64 KiB |
|---|---:|---:|
| 每完成帧 gate 回传字节均值 | 58,468.59 | 119,482.44 |
| 每完成帧候选行读取调用均值 | 32.44 次 | 10.99 次 |
| 每完成帧候选行读取阶段耗时均值 | 36.99 ms | 7.73 ms |
| 总检测 FPS | 241.40 | 279.67 |
| TPU 采样平均 | 83.02% | 95.66% |

**多传了一些连续数据，减少小块读取调用，吞吐反而提升约 15.85%。** 这说明调用和等待成本值得优化，不能只盯每秒字节数。读取阶段是 API 墙钟耗时，包含等待，不能当作纯 DMA 时长；抽帧下两次性能运行选中的源帧也未逐帧配对。实验条件和另外进行的同帧结果一致性检查见[20 路合并实测](device0-capacity.md#20-路64-kib-小块回传合并)。

实际使用：要求两卡接近满载时用 `--mode stress`，本板为 Gen2 ×1 20 路 + Gen3 ×2 32 路；要求每卡都显示 32 路时用 `--mode showcase`，接受 Gen2 ×1 的较低检测速率及利用率。这里的满载指已测区间的采样表现，不保证每个瞬间为 100%；1080p25、独立摄像头以及连续四小时仍需要对应条件的完整验证。

## 后续优化与验证方向

以下是待验证方案，当前版本尚未实现预览异步化，也尚未证明这些方案能让 Gen2 ×1 的 32 路接近满载：

1. **先拆分图像处理计时。** 分别记录预处理 VPP、数值转换及提交／同步耗时；需要 SDK／驱动侧证据才能继续区分实际执行与排队等待，不能把整个调用耗时当成硬件执行时间。
2. **在相同配置下隔离预览影响。** 固定同一卡、32 路、模型、输入、合并预算、记录方式及另一张卡的负载，对比正常预览与暂时关闭预览。关闭预览只用于定位，不能作为满足 HDMI 展示需求的最终结果。
3. **再验证预览与推理分离。** 尝试将预览缩放、回传放到独立工作路径，用容量受限的最新帧队列避免积压，保留源图像直到预览处理完成，并保持图像和检测框同帧。恢复双卡同时显示后，比较总检测 FPS、逐路最低 FPS、源年龄、最长无结果间隔、内存占用和 TPU 利用率，再进行完整四小时测试。
