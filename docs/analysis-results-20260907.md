## 本轮配置与复现

## 实测结果

| 指标 | 单路结果 |
|---|---:|
| 正式采集时长 | 120.44 秒 |
| 平均完整分析 FPS | 13.55 |
| 两个窗口 FPS | 13.50 / 13.60 |
| OpenCV 解码/取帧平均耗时 | 29.52 ms |
| 图像转换＋预处理＋推理＋后处理平均耗时 | 43.69 ms |
| 单帧处理 P95 | 94.60 ms |
| 最大相对读取计划落后 | 69.01 秒 |
| 全程检测结果与 worker 汇总 | 2039 条 / 2039 帧，一致 |
| 编码提交帧数 | 0（未启用） |
| 正常收尾退出码 | 0 |
| 结论 | 帧率和计划落后未达标；检测输出完整性通过 |

2039 帧是含预热及收尾的全程计数；FPS 和分阶段耗时来自正式采集区间，两者口径不同，不应拿 2039 除以 120 秒。计划落后是从本地输入时间表累计的延后，不是测得的摄像头端到端时延或解码队列长度。

`stderr.log` 为空；`progress.log` 中保留 SDK 的 on-chip CPU 初始化提示（两设备启用失败，并说明未使用 bmcpu_opencv 可忽略），本轮未因该提示终止。它是环境记录，不能仅凭提示认定性能根因。

## 可以得出的结论

当前这一版串行解码＋检测实现，单路约 13.55 FPS，未满足每帧 25 FPS 的目标，因此不能按纯解码 30 路的结果外推算法分析容量。没有运行编码，不能把本轮耗时归因于编码。

解码与分析平均合计约 73.21 ms，与当前每帧串行处理速度相符。分析耗时包含 CPU/设备间图像处理与前后处理，尚未细分 TPU 纯推理。纯解码压测使用 FFmpeg 硬件解码后丢弃输出，这里使用 OpenCV 图像交付给检测模型，数据路径不同。以上证据不足以断言芯片推理能力或 PCIe 已达到硬件上限。

## 下一步定位方向

1. 在同一 OpenCV 取帧路径建立无推理对照，测清取帧及图像交付开销。
2. 细分图像转换、预处理、TPU 执行和后处理耗时，检查是否存在多余的主机/设备图像拷贝。
3. 单路改进后重跑相同基线，再评估跨流并发、共享模型与 batch；多进程总吞吐可能不同，但本轮未测，不能推算路数。
4. 客户模型及每路实际分析帧率确定后，按该配置重新阶梯压测；需画框编码时再测试完整链路。
