# 预览与整墙限频拆分对照

2026-09-28，RK3588 + BM1684X device 0，PCIe2 ×1（5.0 GT/s）。本轮把单路预览与整墙限频拆成四种配置，正向和反向各一次，共8组。结论：**读取调用耗时改善在两轮均出现，主要伴随整墙限频取消；尚不能认定PCIe硬件传输延迟本身降低。**

## 条件与口径

固定32路1080p24长素材、YOLOv8s INT8、VPP展开前每2帧取1帧、latest、250ms年龄门槛、reuse、score gate预算64KiB、同步预览。每组30秒预热＋60秒正式统计，ffplay输入参数统一60FPS。顺序为A→B→C→D→D→C→B→A；各组重新启动并从同一素材开头运行。独立实验二进制 `demos/hdmi_wall/build-grab-select/hdmi_wall.pcie`，SHA256为 `eb0168b3d293ff6b8982bce8b7539d272d1a55f4f5815e481f2a5aa5dacd0bbd`。

| 配置 | preview-fps | wall-fps |
|---|---:|---:|
| A 基线 | 3 | 10 |
| B 仅放开单路预览 | -1 | 10 |
| C 仅放开整墙 | 3 | 0 |
| D 两者放开 | -1 | 0 |

以下为两次等时长测量的算术均值。推理解码来自summary正式窗口；TPU来自正式窗口遥测；单路预览为32路正式提交次数除以时长后求平均。整墙提交速率来自正式窗口内status累计计数差，可能包含重复画面，不是每路新画面或物理屏幕帧率。

## 效果

| 配置 | 总推理FPS | 单路预览FPS | TPU均值 | 预览载荷MB/s | 整墙提交FPS |
|---|---:|---:|---:|---:|---:|
| A 基线 | 271.83 | 2.40 | 95.60% | 8.50 | 10.00 |
| B 仅放开单路 | 251.31 | 7.85 | 89.10% | 27.79 | 10.00 |
| C 仅放开整墙 | 279.55 | 2.46 | 98.48% | 8.72 | 50.50 |
| D 两者放开 | 275.38 | 8.61 | 98.60% | 30.46 | 46.80 |

八组解码均约768FPS，逐帧账目完整、无整段零分析通道、无通道错误，全运行过期丢帧为0，正式区间status采样均无STALE。最长无分析结果间隔最大0.287秒，不代表预览间隔或端到端延迟。

D相对A：预览约3.58倍，推理提升1.31%，预览载荷增加约21.96MB/s。C吞吐更高但单路画面仍只有约2.46FPS，不能用整墙50.50FPS解释为运动流畅。B预览更快但推理下降7.55%，不宜仅根据输出阶段变短判断性能提升。

## 回传耗时拆分

| 平均墙钟耗时 | A 基线 | B 仅放开单路 | C 仅放开整墙 | D 两者放开 |
|---|---:|---:|---:|---:|
| 每次预览读取 | 2.84ms | 2.47ms | 1.74ms | 1.65ms |
| 每次预览VPP | 12.55ms | 21.70ms | 7.36ms | 11.33ms |
| 每推理帧结果读取API合计 | 15.33ms | 14.50ms | 8.66ms | 8.12ms |
| 其中分数读取 | 2.29ms | 2.06ms | 1.24ms | 1.11ms |
| 其中候选行读取 | 13.04ms | 12.44ms | 7.42ms | 7.01ms |
| 辅助模型执行（包含同步） | 34.61ms | 22.99ms | 43.44ms | 35.70ms |
| 整个output_copy阶段 | 50.10ms | 37.65ms | 52.21ms | 43.93ms |

结果读取API合计按 `score_gate_measured` 中score_read_ms、row_read_ms、full_read_ms的sum相加，再除以gate帧数。本轮full_read为0。每帧约119.02–119.25KB载荷，候选行约10.64–10.74次读取；不同配置间载荷接近。它是主机调用的墙钟时间，仍包含驱动排队和线程调度，不能当作纯DMA/总线传输时间。

源码中的 `output_copy_ms` 包住整个 `read_score_gated_output`，包括辅助模型启动与同步、读取及CPU组织工作。因此此前约40–50ms的指标不能直接叫“PCIe回传耗时”。C读取时间下降，但辅助执行等待增加，整个output_copy反而略长，这是不能只看该阶段总值的直接例子。

D对比A：预览读取下降41.85%，结果读取API合计下降47.07%，整个输出阶段下降12.32%。辅助执行没有同步下降（34.61→35.70ms）。改善确实出现在读取调用观测中，但物理链路仍是PCIe2 ×1，本轮没有纯DMA隔离基准或驱动级时间线。

## 两轮一致性与开关贡献

| 配置 | 推理FPS 正向/反向 | 预览读取ms 正向/反向 | 结果读取合计ms 正向/反向 |
|---|---|---|---|
| A | 270.78 / 272.87 | 2.856 / 2.829 | 15.708 / 14.955 |
| B | 249.98 / 252.63 | 2.489 / 2.447 | 14.737 / 14.269 |
| C | 280.07 / 279.03 | 1.681 / 1.800 | 8.274 / 9.043 |
| D | 275.73 / 275.03 | 1.639 / 1.667 | 7.961 / 8.270 |

在单路3FPS时取消整墙限频，结果读取15.33→8.66ms（下降43.53%）；在单路不限频时取消整墙限频，14.50→8.12ms（下降44.04%）。而保持整墙10FPS只取消单路限制，15.33→14.50ms（下降5.40%）。两轮方向一致，支持整墙设置与读取等待变化关系更强。

具体机制仍未隔离。整墙不限频改变CPU渲染、管道写入、播放器活动及调度负载，可能影响驱动队列和CPU运行状态；本轮未固定CPU频率、亲和性或做驱动跟踪，不能直接断言某个锁或PCIe本体是原因。仅两次短测，不构成显著性或长稳验证。

播放器stderr保留了Rockchip GL加载提示，部分运行有rawvideo不足整帧提示；实验进程退出码0，测量完整。这些日志未带逐条时间戳，不能仅凭位置断言它们都只发生于退出。未验证物理显示流畅度或玻璃到玻璃延迟。

## 复现与证据

在没有其他同卡实验时运行，输出目录必须不存在：

```bash
cd /userdata/1684X-EP-demo
sudo python3 tools/diagnostics/legacy/run_grab_preview_comparison.py \
  --device 0 --streams 32 --duration 60 --player-fps 60 \
  --modes 3,preview-only,wall-only,unlimited --repeats 2 \
  --output "/userdata/1684X-EP-demo/data/results/preview-factors-$(date +%Y%m%d-%H%M%S)"
python3 tools/diagnostics/legacy/analyze_grab_preview_factors.py <本次输出目录>
```

原始数据已同时保存在本地和板端 `data/results/grab-preview-factorial-20260928/`：metadata、comparison、factor-analysis、逐组command/state/summary/telemetry/stderr，以及逐秒wall-samples。FIFO是管道，不作为本地结果文件复制。分析脚本输出逐轮条件差值，保留原始值便于重算。默认入口和二进制未替换。

体验更顺畅的预览可使用D；偏重推理和少回传可选C，但画面仍是低帧率预览。两者都是本轮条件下的选择，需继续用实际业务视频验证。
