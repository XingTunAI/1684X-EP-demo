# 两份1080p素材差异与STALE诊断

2026-09-28。结论：编码结构和供给频率均影响当前工作流。不能把问题简化为“25FPS不支持”“B帧有问题”或“8个缓冲必定不足”。同画面全I帧副本在24FPS时通过一次短测，在25FPS时仍有通道失效；原始I/P/B编码即使改为24FPS也未通过。

## 素材本身

| 项目 | 原正常素材 | 公路素材 |
|---|---|---|
| 编码/规格 | H.264 Main，1080p24 | H.264 High，1080p25 |
| 原片帧数 | 592 | 1502 |
| 帧类型 | 592个I帧 | I=31、P=494、B=977 |
| 关键帧间隔 | 每帧 | 50帧 |
| 平均码率 | 14.58Mbps | 8.02Mbps |
| 1秒分箱包载荷峰值 | 15.85Mbps | 12.32Mbps |
| 显示时间戳步长 | 约41.667ms | 40ms |
| 显示时间戳倒退/重复 | 0 | 0 |

完整原片逐帧信息来自系统FFprobe软件解析，不将容器文件名当成帧率证据。两份均为正常编码视频；P/B帧不说明文件损坏或有人额外加工。此前长文件只重复封装压缩包，没有重编码。

## 不带推理的解码对照

同卡PCIe2×1、线性输出0、额外缓冲8，独立`decoder_supply_probe.pcie`：不加载模型、不生成小图、不做图像D2H、不启动播放器。先预解一帧、所有线程就绪后使用共同源时钟，帧用完即释放，不长期持有解码表面。

每档预热5秒＋统计20秒，按素材实际帧率供给：

| 素材与路数 | 正式解码FPS | 最慢通道FPS | 最大源滞后 | 结束前最大源滞后 | 最长单次read |
|---|---:|---:|---:|---:|---:|
| 旧素材1路 | 24 | 24 | 4.0ms | 1.6ms | 3.6ms |
| 旧素材32路 | 768 | 24 | 66.1ms | 32.6ms | 64.7ms |
| 公路1路 | 25 | 25 | 4.4ms | 1.2ms | 4.2ms |
| 公路32路 | 800.95 | 25 | 758.1ms | 39.7ms | 592.4ms |

公路32路纯解码能赶上平均供给，但有超过250ms业务门槛的抖动；800.95略高于800包含窗口内追赶，不表示源变快。该结果不能认定带模型、预览和更多持帧后仍能追赶。

再取消源帧率限频，预热5秒＋统计15秒，32路旧素材909.53FPS、公路796.67FPS；最慢单路分别20.8/20FPS。不同线程吞吐不均，单次短窗口值不能视为精确VPU极限。新素材在当前SDK路径下的解码余量更小，且饱和状态下有公平性与长尾问题。这是“完整业务容易积累源滞后”的支持证据，不是每项驱动/硬件成本的归因。

## 业务中的单变量检查

固定32路、PCIe2×1、YOLOv8s INT8、latest、250ms、gate64、同步预览10FPS/路、整墙10FPS、播放器60FPS、每帧retrieve。保持8个额外缓冲，除特别注明外使用线性输出。正式目标为30秒预热＋60秒统计。

| 条件 | 结果 |
|---|---|
| 原公路I/P/B，25FPS、线性8缓冲 | 前轮失败，曾32路全STALE，正式20路零推理 |
| 原公路I/P/B，25FPS、压缩布局8缓冲 | 多数通道STALE，保护停止；改回压缩布局没有恢复 |
| 公路全I帧诊断副本，25FPS、线性8缓冲 | 278.18总INF，但5路正式窗口零结果；27598次全运行过期丢帧、最长分析空窗60秒、状态采样最多15路STALE，业务不合格 |
| 同批全I画面，改按24FPS播放、线性8缓冲 | 277.23总INF、768解码FPS，32路均有结果；最慢8.517FPS、过期0、STALE采样0、最长分析空窗0.248秒；仅一次短测通过 |
| 原I/P/B画面，仅改按24FPS播放、线性8缓冲 | 多数通道STALE，保护停止；减少1FPS不足以修复原编码素材 |
| 原公路25FPS、线性16额外缓冲 | 当前SDK报`the frame buffer count set is wrong`、ret=-17，初始化失败，无有效性能测量 |

保护规则为至少半数通道连续5个约1秒采样STALE，保存`quality-stop.json`并中断本次进程；其`KeyboardInterrupt`不是SDK崩溃。被预热期保护停止的档位没有有效正式FPS，不能把中断summary中的0当作正式测量。

8个缓冲不是一概无效：它在旧素材以及公路全I/24FPS短测中有效；现有数据也没有证明增加缓冲就是正确修复。16是一次临时诊断配置，失败后退出，没有改变默认配置。

## 如何构造公平对照

公路全I副本取原片前20秒（500帧），使用libx264、25FPS、High、8Mbps目标码率、GOP1、B帧0，重复封装成长文件。这是有损诊断转码，不与原片逐像素等价，也同时改变了多个编码参数；不能把收益全部分配给某一种帧。

全I/24FPS版使用同一批500张编码画面，只重封装时序，没有再次编码；软件解码逐帧哈希500/500一致，现场OpenCV报告24FPS。最初尝试改H.264 VUI被系统FFmpeg拒绝，失败日志保留；成功版本仅使用容器时间戳，不能声称VUI已修改。它实际是减慢播放，不是实时源丢帧方案。

原I/P/B素材的24FPS版仅缩放时间戳，1502个压缩视频包SHA256逐包一致，现场OpenCV约24.000017FPS。它保留原有预测帧与画面，不发生视频重编码，同样是诊断性的减慢播放。

全I转码可能增加码率或损失画质，不能把本轮测试解释为推荐生产视频全部改成I帧。全I/24FPS只是一个通过短测的诊断条件，仍未完成长稳、真实摄像头、检测召回率和内存验证。

## 对总INF约280的解释

公路全I/25与24的总INF分别278.18和277.23，数值近乎不变，但前者5路整段无结果、后者全部连续。这直接证明总吞吐不能代替逐路有效容量。模型和辅助计算决定总吞吐的一部分上限，输入持续供给与公平性决定这些计算能否分配到所有通道；当前未分清全部底层机制。

下一步应在原始编码素材下隔离模型/预览持帧、解码服务时间及调度，或测实际容量与主动丢帧/追赶策略。不能直接取消250ms门槛后拿旧帧推理来宣称实时问题已解决。
