# 压测报告阅读指南

适用于[单卡纯解码](single-card-decode.md)和[单卡解码＋推理](single-card-analysis.md)。先确认链路与配置，再解释数值；两者都默认只测性能，旧报告按当时配置保留验收判定。

## 先看哪份文件

1. 打开本轮 `report.md`，确认测试编号、设备、模式、输入、档位和正式采集时长。
2. 查看 `stages.csv` 的总吞吐与最差逐路窗口，再查 `streams.csv` 找到具体哪一路较慢。
3. 有异常时，查看 `run_state.json`、`summary.json` 的原因及对应流的 `stderr.log`；需要追查窗口波动时再分析原始采样。

`report.md` 在开始、每档结束和收尾时自动生成。首次启动时可能只有 config、run_state、报告及空 CSV，首档结束后才有根目录 summary。当前档未结束时显示等待，不等于任务卡死。`watch -n 5 cat report.md` 只是周期性读取报告。

| 文件 | 纯解码 | 解码＋推理 |
|---|---|---|
| `report.md` | 中文档位汇总、异常及文件入口 | 增加模型、图像路径、分阶段和输出核对 |
| `stages.csv` | 每档总平均 FPS、最差逐路窗口 | 增加处理 P95、最大计划落后 |
| `streams.csv` | 每路加权平均 FPS、最低窗口及门槛字段 | 增加各处理阶段平均耗时与输出完整性 |
| `windows.csv` | 当前自动生成器不产出；部分历史目录有额外分析导出 | 当前自动生成各窗口汇总 |
| `config.json` | config 参数及 metadata 探测结果 | 参数、模型哈希、图像路径；新运行另存 worker 哈希 |
| `run_state.json` | 整轮生命周期及结束原因 | 整轮生命周期及结束原因 |
| 根目录 `summary.json` | 已完成或已收尾档位的原始窗口与状态 | 增加检测输出核对和性能判定信息 |
| `step_XX/summary.json` | 单档记录，收尾时保存 | 单档解码调度层记录；最终分析结论以根目录 summary 为准 |
| `step_XX/samples.csv` | 累计完成帧数及最近进度时间 | 同类进度采样，帧数代表分析完成 |
| `step_XX/monitor.jsonl` | bm-smi、主机 CPU/内存/网络原始采样 | 同类资源记录 |
| `step_XX/stream_XX/` | progress.log、stderr.log | 检测 JSONL、worker_summary、进度和错误日志；encode 模式另有视频 |

例如 `step_32` 表示 32 路档位，`stream_00` 表示其中第 0 路。单卡解码报告里没有 windows.csv 并不代表输出失败，逐窗口数据仍在 summary 中。

## FPS 和时延怎么解释

| 指标 | 定义与解释 |
|---|---|
| 单路窗口 FPS | 该窗口完成帧数增量 ÷ 实际窗口秒数 |
| 单路平均 FPS | 按各有效窗口实际时长加权，不是各窗口 FPS 的简单平均 |
| 总平均 FPS | 同一档各路平均 FPS 之和 |
| 平均每路 FPS | 总平均 ÷ 路数，只是均值，不能代表最慢的一路 |
| 最差逐路窗口 FPS | 所有有效窗口、所有流中最低的一个窗口帧率，不是全程平均 |
| 处理 P95 | 分析帧处理耗时的第 95 百分位，不是摄像头到显示的端到端时延 |
| 最大计划落后 | 相对本地源帧读取计划的最大落后，反映追赶/积压，不等于单帧处理耗时 |

预热帧不计入正式平均；短尾窗口可能与前一窗口合并，窗口实际秒数未必正好为 60。进度上报有粒度误差，不能用瞬时读数替代正式统计。没有数据时留空或标未测，不能按零处理。

32×25 的名义输入总量是 800 帧/秒。历史纯解码短测总平均 815.21 FPS、最低逐路窗口 23.26 FPS，表示总量较高但仍存在较慢窗口；不能宣称所有流持续 25 FPS。预热后的追赶和计数窗口会影响总量，超过 800 不能直接作为稳定余量。

当前 32 路解码＋推理总平均 114.10 FPS，平均每路 3.57 FPS。每帧都分析，程序会落后本地输入进度；这个数不是“每秒实时选取 3.57 张最新画面”，本轮没有实现抽帧。独立 TPU 模型计算的 354.50/370.11 图每秒不包含完整视频链路，不能替代此值。

## 完成、通过和失败分别代表什么

| 范围 | 状态 | 含义 |
|---|---|---|
| 单档，两种链路 | `measured` | 测量完成，未应用 FPS 验收；分析链路还要求输出完整及正常收尾 |
| 单档，纯解码历史/显式验收 | `fps_pass` / `fps_fail` | 逐路每个有效窗口达到/未达到配置门槛 |
| 单档，分析显式验收 | `pass` / `fail` | 综合 FPS、计划落后和输出校验的判定 |
| 单档 | `error` | 进程提前退出、停帧或其他运行异常；查 reason |
| 单档/整轮 | `incomplete` | 中断或未完成，已采集数据可保留，但不代表完整测量 |
| 整轮 | `completed` | 所有计划档位正常测完；测量模式不等于容量验收通过 |
| 整轮 | `failed` / `error` | 提前结束或环境/运行异常，结合单档状态和 reason 分析 |

纯解码一键入口退出码：0 表示所有计划档位完成；1 表示中断、运行异常或显式验收未通过；2 表示参数/预检/外层处理错误。以终端、run_state 和单档原因共同判断，不只看最后一个数字。

测量模式下，CSV 中 threshold_fps、fps_ok、below_threshold 等验收字段为空或不适用；这表示没有进行判定，不是“0 路失败”。历史报告的 24.5 FPS 是当时参考门槛，低于门槛不等于解码进程崩溃。

纯解码按计划终止 FFmpeg 后可能留下非零退出码，记录在 `exit_codes_after_cleanup`，不能当作运行中异常。分析 worker 要求正常收尾和输出完整：不能把纯解码的收尾规则直接套到分析结果上。stderr 为空也不能证明没有真实丢帧或时延波动。

## 资源监控怎么解释

纯解码未运行算法模型，TPU 利用率低不能说明解码器没有工作。以正确设备编号的解码进度和日志确认硬解链路；bm-smi 的 TPU 利用率不是视频解码单元利用率。显存占用和进程数也不能单独证明帧率达标。

分析链路的低 TPU 利用率可能伴随取帧、传输、预处理、后处理和调度等待。阶段耗时包含相应等待，不等于纯 CPU 或 TPU 内核时间。monitor 中主机 CPU/网络数据是原始累计计数，需按时间差换算；缺失记录不等于零占用。

## 历史报告与归档

纯解码旧结果可用以下命令按其保存的配置重新生成 Markdown 和 CSV：

```bash
python3 src/single_card_decode/report.py results/decode/实际测试编号
```

只读结果、定时重新生成旧版本报告可加 `--watch`，不会启动解码。它也不会产生尚未完成档位的最终数据。重新生成会更新报告显示时间，应保留原始 config/summary/log，不得修改旧门槛或模式再将结果当作原始结论。

分享时保留整轮目录；视频和模型单独按[素材说明](test-media.md)提供。仓库中的结论文档可直接阅读，`results/` 原始数据不随 Git 提交，链接到本地结果的文件在纯 Git 克隆中可能不存在。
