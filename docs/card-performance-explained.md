# BM1684X-EP：理论计算、实际表现与参数说明

[文档索引](README.md) / [当前数据总览](../demos/hdmi_wall/docs/current-data.md) / [计算流程](performance-calculations.md)

整理日期：2026-09-10。对象为本项目的 RK3588 主机与两张 BM1684X / SM7 PCIe 设备。本次整理已有资料与记录，没有重新启动硬件测试。

**读这张卡的能力，需要分别看芯片标称、模型计算、视频完整流程和长时间稳定性。** 32 TOPS、32 路解码、32 路画面、每路检测 25 FPS 是不同概念。以下数字注明来源和条件，不把不同测试的成绩拼成一个配置的能力。

## 1. 数据经过哪些环节

```text
RK3588 接收压缩视频
    ↓ PCIe 上传压缩码流
卡上 VPU 解码：H.264 / H.265 → 原始图像
    ↓ 卡上图像处理：缩放、颜色转换、归一化等
卡上 TPU 执行检测模型
    ↓ PCIe 回读输出；当前可用 score gate 减少回读
RK3588 CPU 后处理：候选过滤、NMS、坐标还原等
    ↓ 按需在卡端准备小预览并回传
RK3588 拼屏、播放到 HDMI
```

TPU 做神经网络计算，VPU 做视频编解码，VPP 等图像处理路径准备模型输入和预览。它们可以并行，也会共享设备内存及调度资源。主机 CPU、卡端 DDR 和主机与卡之间的 PCIe 都可能影响最终速度。

`EP` 指 PCIe Endpoint，即此处由主机控制的 PCIe 端点设备；它不是额外的一种算力单位。

## 2. 芯片标称与本板实际配置

| 参数 | 单 BM1684X 官方标称 | 如何理解 |
|---|---|---|
| INT8 | 32 TOPS | 理想条件下每秒 32 万亿次整数运算；不是每秒处理 32 万亿张图片 |
| FP16 / BF16 | 各 16 TFLOPS | 对应两种 16 位浮点格式的峰值，不把两项相加 |
| FP32 | 2 TFLOPS | 32 位浮点峰值；不同计算精度不能直接套用同一个峰值 |
| 卡端内存接口 | LPDDR4 / LPDDR4x，理论 68.3 GB/s | 卡内存储与计算之间的数据带宽，不是 PCIe 带宽 |
| 支持的内存容量 | 最大 16 GB | 芯片支持上限；不等于本板实装或程序可分配容量 |
| PCIe 接口能力 | Gen3 ×16 EP，或 ×8 RC + ×8 EP | 芯片能力；实际模组引脚、底板布线和主机协商结果可能更低 |
| H.264 / H.265 解码 | 32×1080p@25，合计 800 FPS | 指所列视频条件的解码标称，不包含 AI 检测 |
| H.264 / H.265 编码 | 12×1080p@25，合计 300 FPS | 指输出编码视频的能力，不能当作解码或检测能力 |
| VPP 等图像处理 | 缩放、颜色转换、裁剪、补边等 | 具体吞吐与尺寸、格式、调用方式有关，本说明不编造统一 FPS |

算力采用[算能 SC7 用户手册第 5 页的 BM1684X 单芯片说明](https://sophon-file.sophon.cn/sophon-prod-s3/drive/23/07/19/14/%E4%BA%BA%E5%B7%A5%E6%99%BA%E8%83%BD%E5%8A%A0%E9%80%9F%E5%8D%A1SC7%20FP300%E7%94%A8%E6%88%B7%E6%89%8B%E5%86%8C.pdf)，不采用其 8 芯片整卡总量。内存、接口、编解码与图像处理按已核对的[官方 BM1684X 彩页 V1.7](https://sophon-file.sophon.cn/sophon-prod-s3/drive/24/03/11/20/BM1684X%20%E4%BA%A7%E5%93%81%E5%BD%A9%E9%A1%B5_V1.7.pdf)记录。这些是单芯片数据，不能直接套用其他多芯片整卡的宣传参数。

## 3. 理论怎么算

### 路数与帧率

```text
解码需求 = 路数 × 每路源 FPS
检测需求 = 路数 × 每路要求的检测 FPS
```

| 场景 | 解码需求 | 检测需求 |
|---|---:|---:|
| 30 路 25 FPS，每帧检测 | 750 FPS | 750 FPS |
| 32 路 25 FPS，每帧检测 | 800 FPS | 800 FPS |
| 当前 32 路 24 FPS，假设每路检测 8 FPS | 768 FPS | 256 FPS |

第三行的 256 FPS 是目标换算示例。抽帧发生在解码之后时，即使只检测 8 FPS，仍须解码每路 24 FPS。当前素材是 24 FPS，不能写成已经验证了 32×25。

### 算力与模型运算量

```text
计算阶段理想 FPS ≈ 同精度每秒运算量 ÷ 模型每帧运算量
```

官方 YOLOv8s 在 640 输入下约有 **11.2M 参数、28.6 GFLOPs/帧**；YOLOv8n 为约 **3.2M 参数、8.7 GFLOPs/帧**。[Ultralytics 模型表](https://docs.ultralytics.com/models/yolov8/)

以 YOLOv8s 做纸面演算：**若将其运算按与硬件峰值一致的规则计数，并理想化为全部以 INT8 峰值执行**，则 `32,000 ÷ 28.6 ≈ 1,119 FPS`。这是理想计算预算，不是该 bmodel 的速度预测。

实际编译图可能有混合精度、数据重排、访存、算子形状和调度开销。不同工具对一次乘加记 1 次还是 2 次也可能不同，因此必须先核对运算统计口径。INT8 模型还可以具有 FP32 输入/输出边界，本项目就是这种情况；这并不意味着整个模型都以 FP32 运算。

本板 YOLOv8s INT8 batch 1 驻留计算约 **372 次/秒**，已明显低于上述理想估算。即使 TPU 显示 100%，也只说明采样意义下持续忙碌，不代表达到了 32 TOPS 的峰值算术效率。

`1000 / 372 ≈ 2.69 ms` 在这里是由总吞吐换算的平均产出间隔。测试有两个并发进程，不能把它直接称为每帧端到端延迟。

### PCIe 带宽

```text
单向编码后上限（字节/秒）
  = 每 lane 的 GT/s × 10^9 × 编码效率 × lane 数 ÷ 8
```

| 链路 | 编码效率 | 单向编码后理论上限 |
|---|---:|---:|
| Gen2 ×1 | 8/10 | 500 MB/s |
| Gen3 ×1 | 128/130 | 984.62 MB/s |
| Gen3 ×2 | 128/130 | 1969.23 MB/s，约 1.97 GB/s |

`GT/s` 是传输次数单位；小写 `b` 为 bit，大写 `B` 为 Byte，8 bit = 1 Byte。这里 MB / GB 使用十进制，MiB / GiB 使用二进制。上表尚未扣除协议、流控和实现开销；PCIe 支持双向传输，但不能把两个方向相加当成单向带宽。[PCI-SIG 编码与带宽说明](https://pcisig.com/how-does-pcie-30-8gts-double-pcie-20-5gts-bit-rate)

Gen3 ×2 的上限约为 Gen2 ×1 的 3.94 倍，不代表视频检测一定快 3.94 倍。并且主机→卡与卡→主机的应用调用实测可以不同。

### 压缩视频、原始图像与模型结果的数据量

以下均为十进制 MB，不含对齐、协议和额外缓冲：

| 数据形态 | 计算 | 数据量 |
|---|---|---:|
| 假设一路压缩视频为 8 Mbps | 8 ÷ 8 | 约 1 MB/s |
| 30 路同样的压缩视频 | 30 × 1 | 约 30 MB/s |
| 一帧 1080p、8 位 YUV420 / NV12 | 1920×1080×1.5 | 3.1104 MB/帧 |
| 一帧 1080p、8 位 BGR | 1920×1080×3 | 6.2208 MB/帧 |
| 750 FPS 的 1080p YUV420 原图 | 3.1104×750 | 2332.8 MB/s |
| 750 FPS 的 1080p BGR 原图 | 6.2208×750 | 4665.6 MB/s |
| 当前模型完整 FP32 输出 | 实测每帧 2,822,400 字节 | 2.8224 MB/帧 |
| 750 次/秒均完整回读输出 | 2.8224×750 | 2116.8 MB/s |

8 Mbps 是换算示例，不替代当前官方素材的实际码率。YUV420 的 1.5 字节/像素也不能直接用于 10 位或其他像素格式。

**“只传检测结果”也可能很大。** 当前完整输出是密集候选张量，尚不是少量最终检测框；750 次/秒全部回读就超过 Gen3 ×2 的单向理论上限。score gate 在设备端计算各候选行的最大类别分数，主机先回读分数、按阈值选择候选，再按需回读候选行，从而减少完整输出回读。

当前 demo 在卡上解码和准备模型输入，完整 1080p 图像并不逐帧回传主机；预览回传的是每路 **256×144 BGR** 小图，再由主机组成一幅 **1920×1080、更新上限 10 FPS** 的视频墙。因此上表的全尺寸原图流量是架构对照，不能冒充当前 demo 的实际总线流量。[当前回传路径与软件计数](../demos/hdmi_wall/docs/pcie-comparison.md)

### 模型参数量、输入尺寸与内存

- **参数量 M**：百万个权重，主要描述模型规模。它与每帧运算量 GFLOPs 是不同指标。
- **权重大小粗算**：参数数目×每参数字节数。11.2M 权重按纯 INT8 约 11.2 MB，按 FP32 约 44.8 MB；不等于 bmodel 文件大小或运行内存。
- **运行内存**：还包括激活、工作区、解码缓存、并发模型实例、图像缓冲和 SDK 保留区。仅凭“16 GB”不能推出多少路。
- **输入尺寸**：视频可以是 1920×1080，模型实际吃的是缩放/补边后的 640×640。降低模型输入到 320×320，在常见卷积结构下像素相关计算大致变为四分之一，但实际加速、编译支持与小目标精度必须验证；原视频解码量不会自动变小。
- **batch**：一次模型调用处理多少张图。若计时为整 batch 耗时 `t ms`，吞吐为 `batch×1000/t`；若工具已经按单图折算，不能再乘 batch。更大 batch 还影响缓存和凑批等待。

## 4. 本板已经测到什么

### 模型与传输隔离：2026-09-10

模型统一为官方 YOLOv8s INT8 batch 1。两卡逐一测，另一张卡空闲；每模式两个进程，预热 3 秒、正式 10 秒。初始化与输入首次上传不计时。

| 模式 | Gen2 ×1 | Gen3 ×2 | 覆盖范围 |
|---|---:|---:|---|
| 驻留模型计算 | 371.83 次/秒 | 371.36 次/秒 | 模型提交与同步；TPU 采样均为 100% |
| 仅完整输出回读 | 104.35 次/秒 | 208.35 次/秒 | 重复读取已生成输出；不计算新模型 |
| 每次计算并完整输出回读 | 77.80 次/秒 | 143.27 次/秒 | TPU 平均分别 20.60% / 41.60% |

这些是探针循环速率，没有视频、预处理、NMS 或 HDMI。当前视频墙减少了回传，不能用 77.80 次/秒替代其实际检测速度。

16 MiB 大块传输，每方向内部循环 10 次、外部重复 3 次，均值如下：

| 方向与计时范围 | Gen2 ×1 | Gen3 ×2 |
|---|---:|---:|
| 主机→卡，应用侧调用 `sys` | 318.86 MB/s | 836.77 MB/s |
| 卡→主机，应用侧调用 `sys` | 145.70 MB/s | 330.00 MB/s |
| 主机→卡，SDK profile `real` | 384.52 MB/s | 1418.33 MB/s |
| 卡→主机，SDK profile `real` | 398.34 MB/s | 1449.42 MB/s |

两种计时范围不同，不能挑其中一个冒充所有业务的有效带宽；尺寸和调用方式变化也会影响结果。原 SDK 输出虽标 MB/s，实际按 MiB/s 计算，报告已转换为上表十进制单位。[完整隔离报告](../demos/hdmi_wall/docs/capacity-validation.md)

### 解码：2026-09-10

素材为本地 H.264、1080p24；不同进程读取相同素材。不限速扫描取消源节流，各档预热 10 秒、正式 30 秒。以下为两卡匹配的 8 路并发组：

| 测量 | Gen2 ×1 | Gen3 ×2 |
|---|---:|---:|
| 纯解码总吞吐 | 959.42 FPS | 969.66 FPS |
| 独立 TPU 满载时总解码吞吐 | 877.74 FPS | 881.89 FPS |
| 相对纯解码下降 | 8.51% | 9.05% |

这里 8 路不限速可以每路远超 24 FPS；路数是并发解码器数量，不是实时播放路数。满载组的模型运行固定驻留张量，**没有消费这些解码帧**。下降约 8%–9% 只适用于本轮匹配条件，不是所有解码加推理场景的固定折扣。

另做的 32 路源节流、正式 60 秒短测，Gen2 ×1 / Gen3 ×2 分别预热 90 / 15 秒，在 TPU 高负载时总解码分别 768.11 / 768.47 FPS，最低逐路 30 秒窗口为 23.69 / 23.70 FPS。36 路出现慢通道，33–35 路没有逐一验证。不能用约 880÷25 的结果宣称已经验证 35 路实时摄像头。[解码扫描及确认测试](../demos/hdmi_wall/docs/capacity-validation.md)

### 旧默认视频墙：2026-09-10 指标验证

双卡同时各 32 路，官方本地 1080p24 素材，YOLOv8s INT8 batch 1，showcase / latest / score gate，正式 60 秒：

| 指标 | Gen2 ×1 | Gen3 ×2 |
|---|---:|---:|
| 实际总解码 | 767.90 FPS | 767.98 FPS |
| 实际总检测完成 | 237.68 FPS | 273.97 FPS |
| 总检测除以 32 的每路平均 | 约 7.43 FPS | 约 8.56 FPS |
| 正式区间 TPU 采样平均 | 85% | 100% |

每路平均是由总量换算，不是逐路最低值。检测流程包含图像处理、推理、后处理及预览相关工作；32 路画面持续更新，并不表示每路 24 / 25 FPS 的所有帧都做了检测。[屏幕指标与本轮记录](../demos/hdmi_wall/docs/wall-indicators.md)

9 月 9 日的另一场正式 120 秒双卡 stress 档，Gen2 ×1 配置为 20 路，检测 282.63 FPS、TPU 平均 97.59%；同场 Gen3 ×2 配置为 32 路，检测 274.30 FPS、TPU 平均 100%。这解释了为什么旧默认低带宽卡采用 20 路接近满载档位，但它不是 20 路×25 FPS。路数与回读预算同时有变化，不能把全部差异归因为 PCIe 代际。[部署档位对照](../demos/hdmi_wall/docs/pcie-comparison.md)

### 新低回传 32 路与回传开关

同日双卡各 32 路、reuse 输出缓冲、每路预览上限 3 FPS、64 KiB 合并预算，240 秒混合模式运行中，恢复 ON 后约 114 秒稳定区间：Gen2 ×1 / Gen3 ×2 总推理 **261.14 / 276.04 FPS**、TPU 平均 **95.18% / 99.98%**。第一个 OFF 稳定区间约 17 / 19 秒：总推理 **312.59 / 314.37 FPS**、TPU 采样均为 **100%**，模型输出和预览字节增量为 0。

两种状态解码均约每卡 768 FPS，受 32×24 的源供给约束。OFF 仍用真实解码帧做预处理和模型计算，但不消费检测输出，同时省掉 gate、后处理及预览，因此不是只隔离 DMA 的实验。逐项条件和证据见 [当前数据](../demos/hdmi_wall/docs/current-data.md)。旧“32 路约 85%”不可继续作为新配置结论。

### 长时间稳定性

2026-09-09 的双卡各 32 路、四小时计划，在入口启动后约 **2 小时 21 分钟**发生 `bmsophon` 消息 FIFO 写入路径的内核 Oops，两卡画面停止更新，未生成最终 summary。该次 TPU 遥测因 `bm-smi` 路径错误全部为空，不能补写为持续满载。

9 月 10 日短测已经能取得有效 TPU 采样，但短测无新异常不等于驱动根因已修复。**四小时稳定性尚未通过**；本轮梳理没有发现后续完整四小时通过的证据。故障调用路径已知，PCIe、供电、固件等最终根因未确定。[长跑故障取证](../demos/hdmi_wall/docs/incident-20260910.md)

## 5. 屏幕读数和配置参数

### 屏幕上看到的数值

| 字段 | 含义 | 容易误解的地方 |
|---|---|---|
| `DEC` / `TOTAL DEC` | 每路 / 全卡成功解码 FPS | 不等于检测 FPS |
| `INF` / `TOTAL INF` | 每路 / 全卡实际模型处理完成 FPS；READBACK OFF 无检测结果可读取 | 不等于模型固定张量探针循环速度 |
| `TARGET` | 已知本地源帧率总和 | 当前 32×24=768，不是 800 |
| `TPU %` | 设备计算利用率采样 | 不是解码利用率，也不是峰值 TOPS 达成率 |
| `Rolling 2s` | 最近 20 个完整的 100 ms 时间桶 | 不等于整场均值，边界与追帧会产生波动 |
| `LAG` | 最近解码帧完成时相对本地计划的落后 | 不只是硬件解码时间；直播无该基准 |
| `AGE` | 距最近一次成功解码多久 | 用来发现解码停顿 |
| `src age` | 当前检测画面从本地计划时刻到渲染的年龄 | 包含处理和旧画面停留时间 |
| `dec age` | 从解码完成到当前画面渲染的年龄 | 不含此前相机、网络、解码器缓存 |
| `drop` | 应用主动舍弃的待检测帧 | 不等于网络丢包；也不意味着未解码 |
| `HDMI cap 10 FPS` | 整幅视频墙更新上限 | 不是显示器物理刷新率或每路检测速率 |
| `P95` | 所统计样本中约 95% 不超过的值 | 不是最大值；仅完成帧的 P95 可漏掉长时间无结果 |

LAG、AGE、src age 对应不同计时边界，甚至不同帧，不能直接相加。真实相机到屏幕延迟需要额外测量。summary 模式每项指标最多保留 4096 个分位数样本，超过后 P95 等属于近似统计；帧数与均值仍使用全部有效观测。`accounting_complete=true` 允许主动丢帧，不等于每个源帧都完成检测。[屏幕字段](../demos/hdmi_wall/docs/wall-indicators.md) · [记录与计时口径](metrics.md)

### 真正改变处理方式的参数

| 参数 | 影响 |
|---|---|
| READBACK ON / OFF（R） | 同时切换所有卡的结果消费与预览回传；不关闭真实解码帧的模型推理 |
| `--preview-fps` / profile 的 `preview_fps` | 每路检测缩略图回传上限，独立于推理限频 |
| `--output-buffer reuse` | 复用模型输出设备缓冲 |
| `--streams` | 每卡创建多少路；多路仍分享该卡资源 |
| `--model n/s` | 选择模型规模；必须同时看速度与场景准确率 |
| `--policy latest` | 持续解码，等待槽保留最新帧；检测忙时覆盖旧帧 |
| `--policy all` | 串行逐帧对照；算不过来时可能落后源进度 |
| `--infer-fps` | 每路启动检测的速率上限；0 不限频，仍不保证逐帧检测或 TPU 满载 |
| `--max-frame-age-ms 250` | 解码后发布及送检时剔除超龄帧；完成检测后的年龄仍可能超过 250 ms |
| `--score-gate on` | 用辅助模型计算行分数，主机据此筛选并按需回读候选行；增加的辅助工作也有成本 |
| `--gate-merge-budget-kib` | 每帧可额外读取非候选行的字节预算，以合并小块调用；不是总线带宽上限 |
| `--image-path` | 选择设备图像转换路径；auto 优先适用的 YUV 路径 |
| `--prime-local-decoders on` | 共享源时钟启动前预取本地首帧，改善启动衔接；不提高芯片标称算力 |
| `--record-mode full/summary` | 逐帧写记录或仅汇总，影响记录开销与分位数保存方式 |
| `--duration` / warmup / window | 分别控制正式测量、预热、统计窗口；不能把预设时长当作已完成时长 |

各入口接受的参数与默认值不同。例如普通 `multi_run` 默认检测上限 5 FPS，showcase 默认不限频；不能把别的入口参数直接追加给 showcase。`policy all` 要求检测限频和年龄门槛均为 0。[完整参数表](../demos/hdmi_wall/docs/parameters.md)

## 6. 如何判断业务目标是否实现

对于 **单卡 30 路、1080p25、每路每帧检测**，需要同时达到解码 750 FPS、检测完成 750 FPS，并检查逐路窗口、持续落后、结果正确性与长时间运行。

现有 YOLOv8s INT8 batch 1 路径的驻留模型计算约 372 次/秒，新低回传 32 路视频墙总检测约 261–276 FPS；关闭结果消费后真实视频模型处理约 313–314 FPS，但不提供检测结果。上述已测路径均未实现该目标。单看 32 TOPS、解码约 970 FPS、TPU 100% 或屏上 32 个格子，都不足以得出已经实现的结论。

一个可复核的描述应同时写明：**卡与实际链路、软件版本、源编码/分辨率/码率/FPS、模型/精度/输入尺寸/batch、路数与抽帧策略、回传及显示方式、正式时长、总量与最差逐路指标、正确性和异常情况。** 本地重复素材、短时吞吐与固定输入一致性均不能代替真实场景的检测准确率及长稳验证。
