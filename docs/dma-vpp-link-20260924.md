# 同卡DMA上限与VPP/DMA混合负载（已完成）

> 阅读顺序：4。主要目的：测量同卡PCIe2/3的SDK有效吞吐及DMA与VPP共存干扰。 [返回阅读导航](pcie-reading-guide.md)。

目标：分离应用DMA可达吞吐、小块调用成本与VPP共存干扰。不能用应用吞吐平台直接宣布PCIe物理线速已饱和。固定device2/0003:31:00.0、同rootport0003:30:00.0，实际速率8→5→5→8GT/s、宽度x1；结束恢复原8GT/s。原驱动及业务二进制不变，使用独立dma_vpp_probe。

每批26档，共104档，各2秒预热8秒正式，后两批反序：

- DMA单独：32KiB、1MiB、16MiB，各上传、下载、独立全双工，每方向1线程；16MiB补每方向4线程；64MiB补单方向1线程。
- VPP单独：2/32线程，驻留NV12 1080p灰图到256x144BGR，BT709 linear。
- VPP加限速下载：2/32 VPP线程，32KiB、110592B、1MiB三种块，目标40MB/s。必须核对实际流量是否达到目标，未达目标的组不能声称等流量。
- VPP2加40MB/s上传；VPP2加不限速大块上传、下载、全双工。

每线程独立handle/主机与设备缓冲；计时前分配和初始化，结束后逐字节校验DMA以及VPP输出一致性及灰值。所有线程共用单调时钟计时窗口，只计完整落入窗口的调用。全双工上传/下载独立报告，不能相加冒充单方向能力。host内存为普通vector，若SDK映射/缓存/驱动限制吞吐，应用上限不等于线速。

每250ms读取/proc/bmsophon/card2/bmsophon2/cdma_*计数和时间；它们是驱动累计指标，不是PCIe字节/硬件链路利用率，初始化和校验也会改变计数，需按正式窗口分析；具体计时语义未查清前不换算占用率。无function_graph/strace。探针启动前已通过双向DMA+VPP及40MB/s限速下载+VPP冒烟与输出校验，不能把冒烟当正式结果。

证据目录data/results/dma-vpp-link-20260924，入口tools/diagnostics/run_dma_vpp_matrix.py。第一层回答当前SDK路径的有效吞吐上限；第二层比较等流量不同块大小对VPP的影响，检验调用频率及共享资源干扰。即使观察到干扰，也不直接指定驱动锁或总线带宽为唯一原因。真实32路业务机制仍需对应验证。


## 实测结果（2026-09-24）

104档全部成功，所有线程均有完成调用，DMA/VPP输出校验通过；527个原始普通文件逐一SHA256一致。四批实测链路为8→5→5→8GT/s、均x1，命令参数与计划逐档核对，监督脚本确认探针哈希前后一致。结束state及再次读取sysfs均确认恢复8GT/s x1。每档仅8秒正式窗口，两轮结果不能代替长稳测试。

### 当前能确认什么

1. 在本SDK及普通主机内存路径下，PCIe2 x1实测最高上传359.66MB/s、下载340.79MB/s；PCIe3 x1分别689.96和568.33MB/s。均来自16MiB块、每方向4线程的单向测试。它们是本矩阵测得的有效载荷吞吐最高值，不能宣称物理线速已打满。
2. 并发明显影响可达吞吐。例如PCIe2下载16MiB，单线程155.19→4线程340.79MB/s；单纯把块加到64MiB只有151.00MB/s。因此不能把单线程平台直接当PCIe接口上限。
3. DMA与VPP存在可复现的共存干扰。PCIe2的VPP2独跑2855.69calls/s，加不限速上传降至611.88（约下降78.6%），加下载1841.12，加双向432.31。PCIe3也有同类下降。全双工不保证SDK、DMA与VPP控制路径完全独立。
4. 低流量并非完全无影响：约39.92MB/s、110592B块下载时，PCIe2 VPP2为2741.50，相比独跑下降约4.0%；PCIe3为2869.19，下降约1.1%。但32线程组部分混合结果高于独跑，不能宣称所有并发下均单调下降。
5. 没有证实“小块调用次数越多就是唯一主因”：PCIe2 VPP2的32KiB组实际仅38.48MB/s，未严格达到40；110592B组与1MiB组接近40时，大块组VPP反而更低。调用频率、单次占用和调度仍需拆分。

### 边界与下一步

本探针没有解码、推理及真实帧布局；不能把此处VPP吞吐下降比例直接套到32路视频墙。此前同卡业务结果已证明降速使带预览吞吐下降17.1%，本轮进一步证明DMA/VPP混合存在干扰，但还不能定位某一把驱动锁、某个硬件引擎或控制事务为唯一根因。

驱动counter/time仅按正式窗口内首末采样计算差值，保存formal-counter-deltas.json；采样跨度略小于8秒。未把它们换算为链路占用率或硬件忙碌率，计时语义尚未审计。尤其不能用本业务约43MB/s回传有效载荷与独立DMA最高值简单相除，替代真实总线测量。

后续应结合驱动源码明确DMA与VPP命令提交是否共享串行路径，并对真实32路业务作调用次数、单次大小和等待点分解；必要时使用可靠PCIe字节计数/分析工具判断物理总线是否饱和。本轮不修改驱动、不切换业务默认配置。
