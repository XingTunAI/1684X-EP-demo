# 1080p25换素材失败记录：32路全部STALE

后续已完成[素材、纯解码与同画面帧率对照](material-diagnosis.md)：原素材全I、公路素材I/P/B；纯解码公路32路可追赶但抖动较大，全I25FPS仍有通道失效，全I24FPS短测通过，原I/P/B改为24FPS仍失败。以下保留初轮故障现场，不将当时判断改写成最终根因。

2026-09-28。本轮不能作为有效32路性能结果。线性输出＋8个额外缓冲在之前1080p24素材上的短测通过，不代表对所有1080p素材适用。

## 配置

新源为`highway_1080p25.mp4`：H.264 High、1920×1080、25/1 FPS、约8.015Mbps、60.08秒、包含B帧。使用系统FFmpeg无重编码重复封装到240.08秒，长文件仍为25/1 FPS。manifest保存原始及长文件SHA256、实际命令和ffprobe信息。

32路读取同一本地长文件，YOLOv8s INT8，线性输出0、额外缓冲8、latest、250ms过期门槛、reuse、gate64、同步预览上限10FPS/路、整墙10FPS，播放器60FPS。第一轮30秒预热＋60秒正式，每帧retrieve。

这同时换了视频内容、码率和编码结构，不能把故障归因于单独增加1FPS。未发生应用EOF重新打开；异常在第20秒前后即大量出现，早于约60秒的拼接边界。

## 观测

| 测试 | 结果 |
|---|---|
| PCIe2，32路，每帧取出 | 正式总推理19.63FPS；20路整个60秒窗口零推理；全运行64345次过期丢帧；最长分析空窗60秒；状态采样确有32路全STALE、瞬时0FPS |
| PCIe3，32路，每帧取出 | 同类退化，自动保护停止前23路STALE、解码约683.5FPS、推理63.5FPS、最大解码源滞后约2.67秒；不是完整正式窗口 |
| PCIe2，32路，每2帧取1帧 | 同类退化，自动保护停止前23路STALE、解码约710FPS、推理52FPS、最大解码源滞后约3.03秒；不是完整正式窗口 |

后两行是停止前状态快照，不能与第一行正式60秒均值横向算加速比。保护条件为至少一半通道连续5个约1秒采样STALE，保存`quality-stop.json`后中断监督脚本，并清理本次业务/播放器进程。记录中的`KeyboardInterrupt`是诊断主动停止，不是SDK崩溃。

第一档正式解码平均775.15FPS，低于32×25=800FPS的源供给。状态时间序列显示约第20秒已有24路STALE，第50秒31路，第60秒32路，解码源滞后从数百毫秒增长到数秒，最大采样超过10秒。解码状态仍显示OK、近期仍有新解码帧，不是简单全部解码线程退出。

`source_age_ms`是最后展示/分析帧的源年龄；其数十秒值不能冒充当前解码帧滞后，应使用`decode_source_lag_ms`区分。程序`failed=false`和最终`accounting_complete=true`也不等于业务有效，必须检查逐路推理、过期和连续性。

## 当前能够下的结论

1. 用户观察的全部STALE被状态日志证实。此轮业务失败，不能拿总FPS做有效容量结论。
2. 供给持续落后，随后触发250ms门槛丢弃；这是已确认的直接程序路径。
3. PCIe3也复现，不能仅靠升级链路修复；提前每2帧取1帧也未恢复。
4. 尚未区分解码计算/内存能力、线性帧生命周期与缓冲占用、线程调度的贡献；不足以断言VPU硬件极限或驱动缺陷。
5. 不能通过关闭年龄门槛把陈旧画面重新送入推理，再宣称实时问题修好。本轮没有这样处理。

下一步若继续定位，应先隔离纯解码与推理持帧影响，在同素材、同卡下对照输出布局和缓冲数量，再检查逐路源滞后及公平性；降低路数可作为容量诊断，但不能冒充32路修复。本轮未完成这些后续实验，也没有宣称修复。
