# 线性解码输出叠加每2帧取1帧：ABBA验证

2026-09-28。结论：组合可运行，本轮没有明显额外吞吐收益；连续性出现改善迹象，但不足以宣称长期稳定性提升。

## 配置与方法

单卡 device 0，PCIe2 ×1（实读5.0 GT/s、宽度1），32路同一本地1080p24长素材，YOLOv8s INT8。所有档位均使用线性输出 `output_format=0`、额外解码缓冲 `extra_frame_buffer_num=8`、latest、250ms年龄门槛、score gate、64KiB合并预算、输出缓冲复用、同步预览上限10FPS/路。整墙与播放器沿用10FPS配置。

同一独立 `build-grab-select/hdmi_wall.pcie`，唯一计划变量为 `--retrieve-every 1/2`；按1→2→2→1执行，各档预热30秒、正式60秒。未启用内核函数追踪。进程内诊断包装库设置解码参数，32路每档的两项实际参数覆盖日志均核对通过，默认程序及SDK未替换。

这与此前压缩布局、预览上限3FPS的选帧实验条件不同，不直接横向比较历史绝对值。线性布局已不需要解码布局展开，隔帧不再重复节省这一步；后续模型预处理和预览仍使用VPP。全部源帧仍解码，取帧前跳过计数不是节省的VPP调用数。

总吞吐仅增加0.434%，没有足够证据认定有实际加速；两组TPU都已约97%。预览速率也基本一致。组合两轮连续性良好，而基准一轮出现异常，提示组合可能对持续供给有益，但当前仅一组ABBA、每档60秒，尚未量化重复运行中的异常概率，也没有证明异常根因。

组合在24FPS源下最多向后续提供12FPS/路，并非全帧分析；本轮没有新增检测召回率或逐像素一致性验收。原探针的像素检查不能自动替代本组合的正确性验收。未完成RTSP、多码流、长稳与内存增长检查，不作为默认部署切换依据。

播放器日志有既有Rockchip GL驱动加载错误，播放器未失败退出；本报告中的预览FPS是应用生成/提交计数，不代表物理HDMI呈现验收。

## 证据与复现

板端原始目录 `/userdata/1684X-EP-demo/data/results/linear-grab-abba-20260928/`，本地主仓库同名 `data/results/` 子目录保存副本。176个普通文件逐一SHA256校验通过；4个FIFO特殊文件未复制。包含每档命令、配置、逐路summary、遥测、stdout/stderr、拼屏及comparison。`manifest.json`保存板端校验值，`local-verification.json`保存本地汇总。业务二进制、包装库、实验脚本哈希在`artifacts.sha256`。

测试结束无本次业务/播放器进程残留，链路仍为5.0 GT/s ×1。没有改默认启动器、业务二进制或安装库。

复现限定本板device 0、32路及已存在的模型、长素材、包装库；先确认没有同卡业务占用，输出目录必须是新目录：

```bash
cd /userdata/1684X-EP-demo
sudo python3 tools/diagnostics/run_linear_grab_comparison.py \
  --device 0 --streams 32 --steps 1,2,2,1 --duration 60 \
  --output /userdata/1684X-EP-demo/data/results/linear-grab-abba-new
```

包装库是诊断手段，不是生产部署方案。正式采用前应使用受支持的解码参数入口，并验证帧生命周期、内存及业务正确性。
