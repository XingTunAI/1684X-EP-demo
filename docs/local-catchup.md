# 本地视频墙落后追赶实验

**2026-09-23 结论：输入长期断供明显改善，但未通过流畅实时预览验收，也没有达到 TPU 跑满。默认关闭，板端默认二进制保留原版。**

## 双卡交换实测

每轮两卡同时运行，正式窗口各 60 秒，预热 15 秒。结果回传和缩略图回传开启，250ms 送检年龄限制保留。两轮正式窗口分别重叠 59.977、59.916 秒。

| 卡片 / 模式 | 总检测 FPS | 最低单路 FPS | 无正式结果路数 | TPU 平均占用 | 最长无结果区间 |
|---|---:|---:|---:|---:|---:|
| device 0 原版 | 10.55 | 0 | 23 | 3.87% | 60s |
| device 1 追赶版 | 129.27 | 2.88 | 0 | 41.27% | 9.06s |
| device 0 追赶版 | 109.75 | 2.40 | 0 | 35.87% | 8.16s |
| device 1 原版 | 15.55 | 0 | 24 | 5.23% | 60s |

追赶版两轮完成结果的源年龄均值为 83.73 / 92.26ms，最大 357.40 / 452.46ms。250ms 是推理前检查，不限制后续推理和预览完成时间。上述年龄只统计已完成结果；画面等下一次更新时会继续变旧，因此不能用这个均值声称屏幕始终低于 100ms 延迟。

追赶版正式窗口发生 228 / 233 次跳转，跳过 36,766 / 37,873 个源帧；平均跳转准备开销为 1092 / 1305ms。跳帧和秒级更新空窗仍然明显。两张卡实验均正常退出，32 路账目完整；这验证本地文件追赶机制可以恢复输出，不是正式产品验收。

原始数据：[完整有效实验](../data/results/catchup32-drain-20260923/catchup-analysis.json)、[首版失败实验](../data/results/catchup32-20260923/catchup-analysis.json)、[第二版中断实验](../data/results/catchup32-adaptive-20260923/plan.json)。失败轮不纳入成功对比。

验证包括板端 6 项 C++ 测试、Windows 68 项启动器测试、4 项原对照脚本测试，以及源视频/分段像素一致性检查。实验代码已在主仓库 `C:\QIU\XingTunAI\1684X-EP-demo`。

下一阶段需要在保留硬件解码器的前提下按关键帧丢弃落后的压缩输入，避免反复销毁/重开；或者降低送入解码器的总帧率/分辨率、分摊到更多卡。摄像头场景还必须测真实源时间戳和缓冲队列，不能照搬本地文件索引。

## 功能范围

此功能默认关闭，仅用于本地恒定帧率 H.264 文件、`latest` 策略、循环播放和正数过期门槛。不是 RTSP 摄像头方案，也不代表 32 路逐帧实时处理能力。

原流程按固定源时间推进。解码赶不上 32×25 FPS 时，新解出来的旧内容也会超过 250ms 门槛，推理输入可能长期断供。关闭过期规则虽然恢复吞吐，却可能显示数十秒前的内容。

实验功能保留源时钟和 250ms 规则：落后时跳到未来的真实关键帧，准备好后等到该帧原本的播放时间再发布。每次跳过的源帧单独计数，不计为成功解码，不假装完成推理。代价是跳帧和更新间断，必须同时报告结果年龄和最长无结果时间，不能只看 TPU 利用率。

## 数据与解码器约束

- SDK `CAP_PROP_POS_FRAMES` 探针中，请求 10、30、55 帧实际得到 7、27、52 帧；输出未提供有效 PTS，因此不能用它的帧号证明追赶正确。
- 准备工具按关键帧复制压缩码流为片段，不重新编码。逐帧软件解码 MD5 与原始文件全部一致才生成索引。
- 当前 highway 素材为 1502 帧、25 FPS、31 个片段；额外使用 SOPHON 硬件解码比较第 0、1、29、30 个片段开头共 17 帧，像素哈希全部匹配原文件顺序解码。
- 首版只预留 250ms，但 32 路解码器重开平均约 4 秒，两个卡上的正式检测 FPS 都为 0；该实验失败。
- 第二版按实际重开成本增加准备时间，恢复了部分输入，但出现 `bmvpu_dec_delete` 阻塞，缺少完整测量结果；不能作为成功实验。
- 当前版在关闭解码器前等待已发布帧的消费者释放硬件图像；保留真实时间戳，并用观测到的重开成本调整准备时间。验证结果见本页后续记录。

## 复现

在板端仓库根目录，先使用新的输出目录准备索引：

```bash
python3 tools/diagnostics/prepare_catchup_segments.py \
  --input data/inputs/highway_1080p25.mp4 \
  --output data/inputs/highway-catchup-new

HDMI_BUILD_DIR="$PWD/demos/hdmi_wall/build-catchup" bash demos/hdmi_wall/build.sh
```

双卡对照工具要求保留原版二进制 `.tools/catchup-baseline/hdmi_wall.pcie`，并准备好两个空闲 PCIe2 卡 device 0/1。它不会自动终止其他任务。

```bash
python3 tools/diagnostics/run_catchup_comparison.py \
  --output data/results/catchup-new \
  --index data/inputs/highway-catchup-new/index.json \
  --warmup 15 --duration 60
python3 tools/diagnostics/summarize_catchup.py data/results/catchup-new
```

每轮两卡分别跑原版和实验版，下一轮交换角色。每卡 32 路，预览 10 FPS 上限，结果和缩略图回传开启，score gate 开启、合并预算 64KiB。正式窗口约 60 秒，实际重叠时间另列。两卡各有自己的启动屏障，不是同一个硬件同步屏障。

普通 `run.py` / `multi_run.py` 也支持 `--local-catchup-index`，但需要先构建含该功能的默认二进制，且 `--input` 必须对应索引的原文件。当前板端默认二进制没有被实验版替换。

## 验收边界

必须检查 `status=measured`、`accounting_complete=true`、32 路均有正式结果、源帧跳过数、真实结果年龄、最长无结果区间和进程正常退出。只有平均 FPS 增加或 TPU 占用提高不算通过实时视频墙验收。GOP 较长或重开解码器较慢时，此方案可能仍有秒级停顿。
