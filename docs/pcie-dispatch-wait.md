# PCIe 控制访问与驱动等待的进一步拆解

用途：区分一次 SDK 调用、一次驱动寄存器访问和一次 PCIe 线上事务；结合 32 路业务说明“等资源”和“发命令”分别发生在哪里。返回[阅读导航](pcie-reading-guide.md)。

**本轮结论：** 同卡无追踪单次 GET_REG 连续读取约 PCIe2 **2.29 µs**、PCIe3 **1.70 µs**；真实观测到 VPP 取得名额后仍等待 CDMA 的毫秒级案例。不过 32 路对照中出现过期丢帧、个别通道整段零分析和负载波动，尚不能给出各机制解释吞吐差距的比例。没有修改默认驱动或视频墙策略。

## 测量口径

本轮同时安排两种独立实验，按顺序执行，没有将微基准叠加到视频业务：

1. **32 路驱动分账**：设备 2、同卡同插槽，8→5→5→8 GT/s，均 x1；每速率两轮 `none` / `sync10`，后两批反向。每档 20 秒预热、60 秒正式，保持原素材、模型、`build-async` 二进制与 `gate64reuse`。正式窗口中分别取 VPP / DMA / TPU API 各 2 秒、寄存器路径 0.3 秒的函数图。这里的 60 秒业务结果包含追踪扰动，不能替代此前无追踪性能基准。
2. **独立只读访问**：业务退出后，固定 CPU 6，用 `BMDEV_GET_REG` 读取设备 2 的计时器低 32 位 `0x50010184`。每档连续读 10,000 次，再进行 1,000 次读后请求休眠 1 ms 的间隔读取。计时区间是用户态 `ioctl` 的开始至返回，包含系统调用、驱动处理及寄存器读取完成。另跑同规格函数图对照，以识别追踪本身的开销。开关设备句柄不在采样时间内；探针采样不发写寄存器 ioctl，但驱动 open/release 仍有正常初始化及清理。

两者均保留原始文件、命令、同卡实际链路、二进制哈希、计时边界和恢复状态。默认视频墙及驱动不替换。

## 为什么不能把这些数字叫“一条 PCIe 指令耗时”

| 测量层级 | 包含内容 | 本轮能否单独得到 |
|---|---|---|
| SDK 提交 / 同步 | 参数封装、ioctl、驱动排队、固件及硬件完成等 | 已有应用阶段数据，但提交和同步必须分开 |
| 用户态单次 GET_REG | 系统调用、参数拷贝、地址映射查找、MMIO 读及返回 | 独立探针测量 |
| 驱动读取路径 | BAR 地址查找、`ioread32`、主控/设备响应以及函数图扰动 | 本模块将 `bm_read32` 内联，只测得含扰动的 `bm_get_reg` 整段，无法独立拆子函数 |
| 单个 PCIe TLP 在线路上的传输 / 完成 | PCIe 协议、控制器、链路和设备响应 | 当前没有硬件事务分析仪或相应链路计数，仍未直接测到 |

读取通常需要等返回值；写寄存器调用返回并不必然代表写入已经到达设备。Linux 对 PCI posted write 的说明见[设备 I/O 官方文档](https://docs.kernel.org/driver-api/device-io.html)。本轮不向控制寄存器反复写入来做测速。

## 已核对的源码关联

VPP 入口先等待 `vpp_core_sem`，取得两个 VPP 名额中的一个，再准备并经 `bmdev_memcpy_s2d_internal` 上传描述符，最后设置启动寄存器并等待完成。因此，**取得 VPP 名额后仍可能等待共享 CDMA；这个时间会延长名额占用，并让后来的 VPP 调用排队。** 这是源码可确认的串联关系，还需要运行数据判断各段比例。

CDMA 上传与下载共用 `cdma_mutex`。取得锁后，还检查 ARM9 侧 `TOP_CDMA_LOCK`、配置寄存器并等传输完成。不能把锁内全部时间称为 PCIe 有效数据传输，也不能把函数图中任意 `mutex_lock` 都算成这同一把锁。

TPU 提交另走消息 FIFO。`bmdrv_send_api` 的锁、等待 FIFO 空间和写消息，与 `bmdrv_thread_sync_api` 等完成分开统计。同步等待可能包含前序队列、固件执行、硬件执行、中断及调度唤醒；不等于纯资源竞争。

源码位置与库哈希见[控制调用流程](pcie-command-flow.md)及[32 路应用调用账目](pcie-command-costs.md)。

## 数据质量规则

- 函数图逐 TID 匹配，只有完整且父子时间一致的根调用参与统计；边界不完整、栈不匹配或任意层剩余时间小于 -1 µs 的根均剔除，保留异常数与样本完整率。父子包含关系不能重复相加。
- 每 CPU 的 overrun / dropped events 都要检查。没有环形缓冲丢事件不等于文本函数图的所有调用都能可靠配对。
- `schedule_timeout` 包含睡眠、任务执行及唤醒调度；不能都解释为排队。没有采到某个函数，也不等于其成本为零。
- 当前 status 采样与追踪在同一线程，追踪会暂停 status 读取。动态扰动只能按捕获前后累计计数计算**整个捕获会话**的业务 FPS；该跨度包括设置、追踪、导出与恢复。不能称为严格 tracing_on 窗口 FPS。
- 未追踪局部参考要避开捕获会话前后各 2 秒，分别检查前后是否稳定。正式 60 秒汇总含追踪，不能用于更新无追踪性能表。
- 32 路里的大量调用不是大量独立实验。两轮分别保留，特别关注完整率差异和追踪对行为的改变。

## 本轮结果

两项实验均已完成，原始普通文件分别 426 份、45 份，取回后与板端 SHA256 清单逐一一致。结束后独立读回确认 `0003:31:00.0` 为 **8 GT/s x1**、`current_tracer=nop`、函数过滤器恢复。原始数据未覆盖；分析输出单独存放。

### 一次只读访问已经测到微秒级成本

下面是**无函数追踪**的 GET_REG 用户态墙钟，单位 µs。每轮连续读取 10,000 次，间隔读取 1,000 次；固定 CPU 6、无视频负载。第二轮采用反向顺序。

| 实际链路 | 轮次 | 连续读取均值 | 连续 P95 | 间隔读取均值 | 间隔 P95 |
|---|---|---:|---:|---:|---:|
| PCIe3 x1 / 8 GT/s | b0 | 1.6752 | 1.750 | 2.6793 | 2.917 |
| PCIe2 x1 / 5 GT/s | b1 | 2.2821 | 2.625 | 3.1666 | 3.500 |
| PCIe2 x1 / 5 GT/s | b2 | 2.2966 | 2.917 | 3.2457 | 3.500 |
| PCIe3 x1 / 8 GT/s | b3 | 1.7196 | 2.041 | 2.6539 | 2.917 |

按相同样本数合并，连续读取 **PCIe2 2.2894 µs、PCIe3 1.6974 µs**，前者约高 **34.9%**；间隔读取 **3.2061 / 2.6666 µs**，约高 **20.2%**。间隔模式是“每次完成后请求休眠 1 ms”，不保证严格 1 kHz。

这说明在本机现有 CPU/电源策略下，**即使没有视频计算任务的资源竞争，同卡降低 PCIe 速率仍会增加一次控制读取的端到端成本**。它不是所有寄存器、所有写命令和所有 DMA 的通用延迟，更不是一个 TLP 在线路上的纯传输时间。

例如本探针中的 10,000 次同类连续读，累计 ioctl 时间约 **22.89 ms / 16.97 ms**。这只是实测样本成本的等量表达，**没有证明视频墙每秒执行 10,000 次这样的访问**，不能直接换算成整机吞吐损失或总线占用率。

CPU 保持 `schedutil`，没有锁频；无追踪各档前 CPU 6 策略频率记录为 408 MHz，结束时 b0 为 600 MHz，其余为 408 MHz。这些仅为边界快照，不证明中途频率恒定，不能把 0.592 µs 差额全部称为纯链路差。所有样本保持 CPU 6、读取成功且计时器值持续变化。保留原始长尾，不剔除中断/抢占；空时钟对基线单列，不跨轮直接相减。

### 追踪既提供证据，也会改变测量值

同规格开启函数图后，连续读取 ioctl 均值约 **2.51–2.76 µs**，间隔模式约 **5.23–5.74 µs**。因此不能把追踪时的微秒数当作无扰动访问成本。

本轮原始图中 `bm_get_reg` 是 leaf，没有独立 `bm_read32` 子调用。核对安装模块反汇编，`bm_read32` 的地址转换和 MMIO 读取已经内联至 `bm_get_reg`，其中有实际 load 及 `dmb oshld`；所以**没有子函数记录不等于读取时间为零**。可以保留 `bm_get_reg` 整段的追踪耗时，不能伪造一个可分离的 `bm_read32` 数值。当前仍未直接测量 PCIe 线上事务。

四个追踪档均有 11,000 个完整 `bm_get_reg`，与各自 10,000＋1,000 次 ioctl 对齐且 CPU buffer 无丢事件；但内联使子函数分账不可用。聚合结果分别标注 `ioctl_valid=true`、`root_trace_valid=true`、`nested_breakdown_available=false`，不把最后一项缺失误报成整个只读实验失败，也不把缺失项填零。

### 32 路分账：完成采集，但未得到稳定的根因占比

32 个捕获会话中，仅 5 个符合本轮“邻近前后基线充足且漂移不大”的检查；其余会话邻近基线不足或明显波动。以 `sync10` 为例，VPP 根调用均值在 PCIe3 两轮为 **16.41 / 5.60 ms**，PCIe2 两轮为 **2.92 / 2.63 ms**。这些数字既不稳定，也不能取代应用侧预处理/小图计时，更不能据此宣布 PCIe2 等待更少。

**本轮 PCIe2 带预览没有通过所有通道连续分析的要求。** b1_sync10 的通道 25，以及 b2_sync10 的通道 0、2、12，在正式 60 秒内没有完成分析。首次追踪之前已出现持续解码而分析不更新的通道；因此不能把全部异常归咎于追踪。这是保留下来的失败证据，不能把监督脚本正常退出写成业务稳定性通过。

以 b2_sync10 通道 0 为例，第一次追踪前约 19.90 秒的正式窗口里，累计分析数一直是 **32→32**（预热已经完成 32 次），并非进程从未推理。全运行账目为 `decoded 1841 = completed 32 + stale 1749 + overwrite 60`；正式 60 秒解码 1407 帧、完成分析 0。通道 2、12 也有同类情况。命令保留 `--max-frame-age-ms 250`；当前 [main.cpp](../demos/hdmi_wall/main.cpp) 在解码发布前与 Detect 前各有一次 `expired(frame->due)` 检查，计入 `discard_stale`。所以“大量帧因过期在推理前被丢弃”有程序分支与实际计数依据，但 **stale 是全运行计数，不能说正式每一帧都仅因过期而丢弃**，还存在覆盖丢帧。

上述四个异常通道正式窗口的源滞后采样范围约 **0.70–6.76 秒**，显著超过 250 ms 门槛。此处是 status 快照范围，未开启全量解码事件观察，不能还原每张帧的延迟分布。过期规则能解释“为什么这些已解码帧没有喂给 TPU”，仍需进一步区分它们为什么持续落后，以及如何恢复到实时位置。

函数图捕获的是驱动入口，可能同时覆盖预处理、预览和 SDK 内部路径；当前缺少“业务用途→调用线程/调用点”的完整对应。TPU 同步入口也包含快速返回的同步调用与真正等待的调用。业务供给率变化会改变这些样本的组成。

各组 CPU ring buffer 没有记录 overrun/dropped events，但仍有文本调用栈不完整或配对异常，D2S 完整保留率约 88%–96%；解析器严格剔除，不补造时长。该类数据只能用于检查已观测到的调用关系及具体等待案例，**本轮不能给出‘资源竞争占 80%’或‘某把锁解释全部 PCIe2/3 差距’的可信比例**。

当前最稳妥的结论是：控制访问速度有可重复差异；VPP 准入后会串联共享 CDMA 是源码与函数图可核对的路径；但这两项对 32 路吞吐差距的各自贡献仍没有完整定量归因。

一个具体完整调用来自 `b2_sync10/vpp.trace`，TID 21610，行 7547–7830：VPP 总墙钟约 **13.124 ms**，准入约 **1.788 ms**，描述符上传约 **9.865 ms**，其中 CDMA 直接 mutex 调用约 **9.755 ms**，随后完成等待约 **1.428 ms**，其他处理约 **0.043 ms**。子项包含在父项内，不能把 9.865 与 9.755 相加。这个案例证明“拿到 VPP 名额后仍等 CDMA”确实发生过，不能代表平均比例或唯一根因。

下一步应先把业务调用点与 TID 对齐，以低扰动累计计数分离“等 VPP 名额、VPP 名额内等 CDMA、CDMA 持锁控制/完成、TPU FIFO 提交/完成”；将采样线程与追踪控制分开，并保留无追踪整档对照。当前不根据不稳定函数图修改驱动或启用新的默认策略。

## 调用用途标记：代码已加入，实测待完成

新增 [diagnostic_trace.hpp](../demos/hdmi_wall/diagnostic_trace.hpp) 用于后续把业务调用与驱动函数图对应起来。未设置 `HDMI_DIAG_DIR` 时默认关闭，不启动诊断采样线程或写入追踪标记。设置该变量后要求一个不存在的新目录，并要求能够写入 Linux `trace_marker`；`HDMI_DIAG_STREAMS` 默认选择通道 `0,8,16,24`。

启用诊断后，`threads.jsonl` 记录业务线程用途与 TID，`counters.jsonl` 每约 500 ms 记录各路解码、发布前过期丢帧、取帧后过期丢帧和 Detect 完成计数。只有诊断目录中的 `enable` 文件为 `1` 时，选定通道才写入阶段开始/结束标记；控制轮询间隔约 50 ms。函数追踪的配置、采集窗口和恢复仍由外部监督程序负责。

标记阶段为 `decode_read`、`detect`、`preprocess`、`thumbnail`，它们是应用调用范围：解码读取包含节拍等待，预处理包含类型转换，缩图包含像素回传；**不是对应硬件的纯执行时间**。当前仅登记推理业务线程和独立解码线程，不能声称已覆盖异步预览线程或 SDK 内部线程。计数从进程启动累计，Detect 完成也不等于预览完成。

该版本已在独立 `build-role-trace` 目录编译，但用途归因采集及测量扰动验证尚未完成。它是诊断准备工作，不是新的性能优化结论；当前恢复运行的视频墙仍使用原有 `build-async` 二进制。
