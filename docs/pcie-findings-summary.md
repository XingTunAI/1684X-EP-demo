# PCIe2 / PCIe3 性能调查：已知结论与数据总览

更新：2026-09-24。汇总已完成实验，本页不把不同素材、路数、预览策略和追踪条件拼成一组对照。[完整阅读导航](pcie-reading-guide.md)。

需要进一步理解“资源够不够、排队和调度怎么计算”，见[资源占用与等待的计算方法](pcie-resource-accounting.md)。

目前可以确认：**接口速率影响业务；优化回传后仍有共享资源等待和供给不连续；尚未证明视频墙将 PCIe 物理带宽打满，也未量化各机制贡献。** PCIe2 已有 32 路、结果回传和低帧率预览接近满载的短测候选，不能宣称已经通过长稳。TPU 满载不代表 32 路全部源帧均已推理。

**1. 本次测试是什么，哪些不能混比**

- 主业务：RK3588 主控＋BM1684X，当前 YOLOv8s INT8 batch 1、原 1080p24 素材、latest 最新帧策略、250 ms 过期门槛。
- 严格接口对照：同一张设备 2、同一插槽，8→5→5→8 GT/s，均为 x1；模型、素材、程序哈希相同。不是 PCIe3 x2。
- `none`：不生成/回传小图，检测结果仍回传。`sync10`：同步预览，每路上限 10 FPS，不保证实际达到 10，也不限制推理为 10 FPS。
- `model_only`：同时跳过结果读取、gate、后处理和预览，不能当成“只关 DMA”的单变量实验。
- 总 INF 是各路完成推理 FPS 之和；32×24=768 是源帧供给，不是实测推理吞吐。TPU 利用率是遥测采样，阶段耗时是包含排队的墙钟。
- 客户 YOLOv5/SE7 单次约 9 ms、一拖二约 26–30 ms、共享模型及多事件分析，尚未在其 SDK 下完成同模型同计时边界对照，不能用本 demo 直接替客户确定根因。

**2. 数据实际怎样走**

```text
RK3588读取压缩视频 → PCIe上传码流
  → 卡上VPU解码 → VPP预处理 → 类型转换 → TPU主模型
  → 卡上score gate → 回传分数 → 主控筛选/合并候选读取 → 主控后处理/NMS

同一被检测的卡上图像 → VPP缩小 → PCIe回传BGR小图
  → 主控叠框、拼屏 → HDMI显示
```

当前视频墙不编码视频；小图是一张张原始像素，不是完整编码视频流。主控得到检测相关数据和小图后画框，不能据此声称已经交付 1080p 带框视频文件。独立告警系统/网页预览可能采用另一种输出路径，需确认客户实际需求。

| 数据 | 大小 | 是否逐次经过 PCIe |
|---|---:|---|
| 压缩源视频帧 | 按素材码率平均约 75.94 KB | 上传；码率估算，不是每次 DMA 实测 |
| 解码 1920×1080 YUV420 | 逻辑大小 3.1104 MB | 驻留卡内；实际布局可能有对齐/压缩 |
| 640×640×3 UINT8 中间图 | 1.2288 MB | 卡内 |
| 640×640×3 FP32 模型输入 | 4.9152 MB | 卡内；模型量化 INT8 不等于接口为 INT8 |
| 主模型完整 FP32 输出 | 2.8224 MB/推理 | 卡上生成；完整回传模式才整块读回 |
| 优化结果读取 | 平均约 118,876 B/推理 | 33,600 B 分数＋平均约 85,276 B 候选/合并区间 |
| 256×144×3 BGR 小图 | 110,592 B/实际预览 | 生成预览时才回传 |

优化结果数据不是图片，也不只是最终框列表；NMS 仍在主控。单次结果字节相比完整输出减少约 **95.8%**，不等于吞吐提升同样倍数。模型加载是初始化开销，主模型和 gate 的执行命令仍会在运行中提交。

同卡 PCIe2 `sync10`：结果 **25.60 MB/s**＋小图 **17.67 MB/s**＝已计数下行 **43.26 MB/s**；PCIe3 对应 **30.91＋19.04＝49.95 MB/s**。PCIe2 约 74.19% 的推理完成对应小图，摊到全部推理约 **0.201 MB/次**；若本次带一张小图，以平均结果大小估算约 **0.229 MB**。

32 路按原素材 24 FPS 供源，上行压缩码流估算约 **58.32 MB/s**。上下行分开看；这些数没有覆盖全部命令、寄存器、SDK、协议开销。图像/张量卡内大小也不能相加当 PCIe 流量。详见[数据流程](pcie-data-flow.md)。

**3. 最可靠的同卡 32 路接口对照**

每档 30 秒预热、60 秒正式，正反两轮；以下为无函数追踪的基准。最长空窗取两轮最差。

| 场景 | PCIe2 x1 总INF / TPU | PCIe3 x1 总INF / TPU | 实际预览FPS/路：2 / 3 | 最长分析空窗：2 / 3 |
|---|---|---|---|---|
| 优化结果回传，无小图 | 265.37 / 96.25% | 275.93 / 99.88% | 0 / 0 | 0.217 / 0.186 s |
| 优化结果回传，同步预览上限10 | 215.32 / 77.82% | 259.78 / 94.40% | 4.99 / 5.38 | 0.298 / 0.251 s |

同卡从 PCIe3 降为 PCIe2，带预览吞吐下降 **17.1%**；无预览下降约 **3.8%**。恢复速率后性能恢复，确认速率对本业务有影响。无预览 PCIe2 也不是完全没利用 TPU，而是约 96%。

固定驻留图像 VPP 探针则只下降约 **2%**，不能单凭纯 VPP 探针解释视频业务 17.1% 的差距。这些是短测；后续其他测试出现异常通道，不能将此表扩展成所有运行条件下的长期保证。[同卡报告](same-card-link-20260923.md)。

**4. 带宽上限测到了什么**

| 接口 | 理论单向MB/s：扣线路编码，未扣协议 | 本路径实测单向上传MB/s | 本路径实测单向下载MB/s |
|---|---:|---:|---:|
| PCIe2 x1 | 500 | 359.66 | 340.79 |
| PCIe3 x1 | 984.62 | 689.96 | 568.33 |
| PCIe3 x2 | 1969.23 | 本轮无同口径数据 | 本轮无同口径数据 |

实测最高值来自同卡、16 MiB 块、4 线程、上传/下载分别运行，**不能当同时双向保证值或物理线速利用率**。同为 16 MiB、每向 4 线程，真正同时双向时 PCIe2 只有 **210.76 上行＋121.63 下行 MB/s**，PCIe3 为 **421.53＋210.76 MB/s**。

PCIe2 下载单线程 **155.19**，4 线程 **340.79 MB/s**，说明软件路径与并发明显影响有效吞吐。另一块无飞线板为 **343.93 上传 / 348.13 下载 MB/s**；换了平台且重新编译，不能据此认定飞线影响为零。

优化后视频墙的已计数下行 43.26 MB/s，低于纯 DMA 大块峰值；这只能说明没有“小图数据量必然单独耗尽该峰值”的证据，不能直接宣布混合业务无带宽/延迟问题。反过来，若保持 265.37 次/秒而每次回读完整 2.8224 MB，需求约 **749 MB/s 下行**，超过当前 PCIe2 路径能力；这是需求估算，不是 full 模式实际流量。

来源：[DMA矩阵](dma-vpp-link-20260924.md)、[成本口径](pcie-transfer-cost-20260924.md)、[无飞线板](pcie2-direct-bandwidth-20260924.md)。

**5. 已确认的程序调用与资源关系**

- 同步预览位于每路推理循环内，生成并回传小图后才继续下一轮取帧。
- VPP 先取得处理名额，再经共享 CDMA 上传描述符，然后启动并等完成；**取得 VPP 名额之后仍可能等 CDMA**。
- 该驱动的 CDMA 上传/下载共用互斥路径；PCIe 全双工不保证 SDK 端到端互不影响。不能由此说整颗芯片只有一个 DMA 引擎。
- TPU 主模型/gate 另走消息 FIFO 提交与完成同步；不是所有计算单元控制都等同一把锁。
- 卡内计算也需要主控发命令、传参数、读取状态及等待完成，因此卡内 VPU/VPP/TPU 会受 PCIe 交互速度影响。

预览消融：无预览 **264.11 FPS** → 只生成小图、不回传像素 **221.71** → 加小图回传 **213.08** → 完整显示 **210.70**。证明仅增加同步小图生成就会降低吞吐，不能把全部损失归为小图像素带宽；差值不是可普遍相加的独立硬件成本。

混合探针：PCIe2 的两线程 VPP 独跑 **2855.69 calls/s**，加不限速上传后 **611.88**，加下载 **1841.12**，加双向 **432.31**。这是共存干扰证据，不是视频墙损失比例。

最新完整追踪案例：一次 VPP 总 **13.124 ms**＝准入 **1.788 ms**＋描述符上传 **9.865 ms**＋完成等待 **1.428 ms**＋其他 **0.043 ms**；描述符上传内部约 **9.755 ms 等 CDMA mutex**。这是具体实例，不能扩展为所有调用的平均占比。[控制流程](pcie-command-flow.md)、[等待实测](pcie-dispatch-wait.md)。

**6. 单次控制访问和应用阶段时间**

独立只读计时器探针，同卡两轮、固定 CPU 6、无追踪：

| 单次 GET_REG 用户态耗时 | PCIe2 x1 | PCIe3 x1 |
|---|---:|---:|
| 连续读取均值 | 2.29 µs | 1.70 µs |
| 每次读后间隔约1 ms | 3.21 µs | 2.67 µs |

包含 ioctl、驱动与 MMIO 往返，不是单个 TLP 的线缆时间。CPU 使用动态频率，不能把全部差额分配为纯 PCIe 传输。安装模块将 `bm_read32` 内联到 `bm_get_reg`，函数图不能再独立分出该子函数；微秒追踪本身有可观开销。

同卡 32 路 `sync10` 的应用计时，单位 ms：

| 阶段 | PCIe2 x1 | PCIe3 x1 |
|---|---:|---:|
| 预处理整段 | 67.41 | 40.48 |
| 主模型提交 | 0.076 | 0.065 |
| 主模型同步 | 21.49 | 31.88 |
| gate提交 / 同步 | 0.084 / 20.61 | 0.077 / 30.86 |
| 分数读取 | 2.07 | 1.11 |
| 每检测帧候选读取合计 | 11.87 | 5.58 |
| 每张小图VPP | 30.33 | 16.96 |
| 每张小图回读 | 2.69 | 2.03 |

PCIe3 同步更久但总吞吐更高，说明不能用同步均值判断纯 TPU 运算速度。32 路并发，阶段均值不能相加推导全卡 FPS，累计线程时间也不是硬件利用率。

同一窗口每秒主模型＋gate 提交 **430.65 / 519.57** 次，候选区间读取 **2321.20 / 2803.63** 次；每检测帧约 **10.78** 次候选读取。平均约 119 KB 结果不是一次读取。以上是 SDK/API 次数，不是 PCIe 包数，也不能拿空闲 GET_REG 耗时乘这些次数推算所有命令成本。[应用账目](pcie-command-costs.md)。

**7. 哪些优化有收益，哪些失败**

下列每行来自各自对照，不能横向拼成唯一基准。

| 实验 | 数据 | 当前判断 |
|---|---|---|
| 32路筛选后合并读取 gate0→gate64，无预览 | 212.05→264.96 FPS；TPU76.66→96.69%；结果12.27→31.53 MB/s | 吞吐约+25%，多读一些字节换取更少零碎调用有价值；最长空窗仍2.903s |
| 合并预算64→256 KiB | 264.96→262.56 FPS；结果31.53→65.51 MB/s | 继续放大无收益 |
| 32路缓冲复用 | 211.62 vs212.74 FPS，两轮差异变号 | 该视频墙场景未见稳定增益 |
| 同步10→异步10预览 | 213.80→250.76 FPS；TPU78.04→92.37% | 最长空窗47.362s，失败，不启用默认 |
| 同频3FPS：sync3→async3 | 246.43→266.96 FPS；TPU90.05→97.90%；实际预览2.32→2.66FPS/路 | 最差单路8.30FPS，最长空窗0.218s；仅两轮60s候选，未长稳 |
| 异步5FPS | 263.51 FPS / TPU97.14% | 最长空窗5.695s，不作为稳定候选 |
| VPP用户态准入0→2/4 | 212.12→177.04/186.75 FPS | 吞吐下降16.5%/12.0%，不采用 |

低预览帧率是画面流畅度的折中，不是免费性能提升。先前普通逐帧 YOLOv8 的 8/16 路也验证了筛选/合并收益与同源帧结果一致，但其数值不能代替 32 路 latest 视频墙。32 路原素材 full 两轮分别有 11/16 个零结果通道，不能把 full 与 gate64 的 FPS 比值当纯回传加速倍数。[回传优化](readback-performance.md)、[预览实验](preview-root-cause-20260923.md)。

**8. 稳定性证据与失败证据**

PCIe3 x1 24 路、推理/预览不主动限频，已完成正式 **3600 秒**：总 INF **284.69 FPS**、平均每路有效预览 **11.862 FPS**、最慢单路推理 **11.856 FPS**、最长分析空窗 **0.134 s**；TPU离散采样均100%，过期丢帧0。结果/小图分别 **33.99 / 31.48 MB/s**，所有通道持续更新。不能推导32路、768FPS或独立RTSP长稳；软件图像提交不等于目视HDMI验收。少量温度遥测为负值，未确认原因；未采主控RSS，不作全系统无泄漏保证。[一小时报告](pcie3-wall24-1h-20260924.md)。

最新 32 路驱动追踪中，PCIe2 sync10 一轮通道25、另一轮通道0/2/12正式60秒零分析，异常在首次追踪前已存在。示例通道0：正式解码1407帧、分析0；全运行 `1841解码=32完成+1749过期丢弃+60覆盖`。32次完成发生于预热。过期丢弃有 Detect 前程序分支与实际计数支持，但全运行丢帧数不能当正式窗口丢帧数。

这些异常通道源滞后采样约0.70–6.76秒，超过250ms门槛；“已解码但没送进TPU”的程序原因已具体化。为什么持续落后、如何恢复公平供给仍需拆解。32个追踪会话仅5个邻近基线质量足够，不能将新追踪均值当稳定无追踪性能，也不能因程序正常退出宣称全部业务通过。

**9. 当前仍不能对外承诺的结论**

- 没有证明视频墙 PCIe 物理带宽满载；没有完整 PCIe TLP 数量、线上控制字节和纯协议开销。
- 没有算清资源准入、CDMA持锁、固件/硬件执行与唤醒对总性能差距各占多少。不能说“已证明调度占80%”或“唯一根因是某把锁”。
- 没有证明 VPP 硬件计算100%饱和、驱动存在错误或必须改驱动；直接删锁会破坏共享资源保护。
- 没有严格同口径的 PCIe3 x2 三方对照，也不能说只有x2才能让TPU满载。
- 没有完成 PCIe2 32路低帧率异步预览的长稳，也没有本模型32×24FPS全帧推理的验收。
- 尚未确认客户回传需求、预览分辨率/帧率、编码位置、多事件负载及其SDK模型共享的并发行为。
