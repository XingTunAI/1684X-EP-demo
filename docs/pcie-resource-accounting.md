# VPU / VPP / TPU：资源需求、占用与等待怎样计算

[已知数据总览](pcie-findings-summary.md) / [阅读导航](pcie-reading-guide.md)。本页说明计量方法和现有数据能算到哪一步，不宣称已完成所有底层计时。

**首先分清三个问题：每秒要处理多少任务；资源实际被占用多久；任务为了等资源或完成通知花了多久。** SDK 调用 30 ms 不能直接解释为硬件计算 30 ms，也不能直接拿来计算硬件容量。

**1. 每种资源的任务量分别算**

以32路1080p24为目标，以同卡PCIe2 `sync10` 的实测完成率作示例：

| 资源/路径 | 工作需求或已观测工作量 | 当前能确定什么 |
|---|---|---|
| VPU | 按原帧率完整解码要求32×24＝768源帧/s | 是需求，不代表本轮实际全完成；latest仍可能只选一部分送推理 |
| VPP预处理 | 每次推理对应一次显式缩放/格式处理，按215.325次推理/s估算 | 不包括未统计的SDK内部调用、桥接、失败/重试等 |
| VPP预览 | 实际约159.7417张小图/s | 上限10×32＝320不是实际完成量 |
| 两类显式VPP合计 | 约215.325＋159.7417＝375.0667次/s | 只是按完成量估算，不是全驱动VPP请求数，也不是硬件任务总数 |
| TPU主模型 | 约215.325次/s | 相同模型、形状、batch、精度才可直接比较单次成本 |
| TPU辅助gate | 约215.325次/s | 比主模型工作不同，不能把两次提交当成两次等量YOLO推理 |
| DMA | 各方向的字节/s、调用/s、块大小分布 | 结果平均119KB仍分成一次分数读＋约10.78次候选读 |

VPU容量与编码格式、分辨率、帧率、参考帧/码流复杂度和内存路径有关；VPP与输入/输出尺寸、格式、裁剪/补边、实际操作组合有关；TPU与具体模型、算子、精度、batch和卡内搬运有关。不能只用“32路”或芯片TOPS直接推导是否足够。已有解码576FPS的24路限速输入测试也不能当作VPU最高能力。

**2. 资源容量按占用时间或同规格吞吐建立预算**

对某种资源r，任务类型k每秒需求为λ_k，每次占用该资源的工作量为S_rk（单位：资源单元·秒），则：

```text
每秒所需资源工作量 D_r = Σ(λ_k × S_rk)
```

如果该资源有m个等价、独立执行单元，且负载稳定，可用 `D_r / m` 粗估容量负担；超过1表示这个资源预算已不足，低于1仍不保证没有突发排队或其他资源阻塞。这是简化的需求预算，不是实测硬件利用率。

例如，**纯假设**某硬件单元每任务真实工作1 ms，需求300次/s，则需要0.3个单元的持续工作能力。若观测到SDK调用10 ms，不能用300×10 ms判断硬件需求为3个单元，因为这10 ms可能大部分在等待。

必须分别使用对应的S：

- VPP准入名额：从取得名额到释放名额；可能包括等待CDMA。
- CDMA互斥资源：从拿到锁到释放锁；包含配置、内部硬件锁等待、搬运与完成通知等。
- VPP/TPU/VPU硬件：真实执行忙时，需要经核验的硬件计数或执行追踪。驱动“启动→收到完成”仍可能包含通知延迟，不能自动当作纯计算。

驱动有两个VPP准入名额，**不等于已经证明存在两个完全独立、可线性扩展的硬件服务单元**。不能把准入数量直接代入硬件容量公式。

**3. 每种等待需要哪些时间点**

```mermaid
flowchart LR
    A[请求VPP名额] -->|准入等待| B[取得名额]
    B --> C[请求CDMA]
    C -->|CDMA锁等待| D[取得CDMA锁]
    D --> E[上传描述符并释放CDMA锁]
    E --> F[启动VPP]
    F -->|执行及完成通知| G[收到完成]
    G --> H[释放VPP名额并返回]
```

| 要计算的量 | 时间点定义 | 不应混淆成什么 |
|---|---|---|
| VPP准入等待 | 取得名额－请求名额 | VPP硬件计算时间 |
| VPP名额占用 | 释放名额－取得名额 | VPP实际busy；期间可能在等CDMA |
| CDMA锁等待 | 取得锁－请求锁 | PCIe实际搬运时间 |
| CDMA锁持有 | 释放锁－取得锁 | 纯线速时间；锁内还可能等ARM9或完成通知 |
| 完成等待 | 收到完成－任务启动 | 纯排队；可能包含固件/硬件执行和通知 |
| CPU调度等待 | 线程已经可运行，却尚未获得CPU的区间 | 整段阻塞时间；线程等硬件时未必可运行 |
| 本次调用墙钟 | SDK返回－SDK开始 | 单纯硬件时间或单条PCIe指令耗时 |

CPU调度应结合同一TID的 `sched_wakeup`、`sched_switch` 等事件配对，并统计被抢占后仍可运行的等待；一次唤醒到获得CPU的差值只覆盖那一次等待。事件可用性和字段应按板端内核检查，不能直接套其他版本格式。方法参考[Linux事件追踪文档](https://docs.kernel.org/trace/events.html)。函数图的sleep-time等选项会影响包含的等待，需要随数据记录，参考[ftrace文档](https://docs.kernel.org/trace/ftrace.html)。

**4. 用已经抓到的样本演示**

一次完整VPP调用为13.124 ms：

| 根一级、不重叠分项 | 耗时 |
|---|---:|
| 等VPP准入 | 1.788 ms |
| 描述符上传整段 | 9.865 ms |
| 后续完成等待 | 1.428 ms |
| 其他 | 0.043 ms |

其中描述符上传内部约 **9.755 ms 是CDMA mutex调用耗时**。它已经包含在9.865 ms里，不能再加到13.124 ms上。`13.124－9.755＝3.369 ms`也不能称为VPP纯计算，因为剩余还有准入等待、其他提交和通知。

这个样本最直接说明：**VPP名额可能被占着，但VPP还在等命令上传，硬件并未开始当前任务。** 若只看名额占用会认为资源很忙，只看硬件busy却可能看见空闲；两者描述不同状态，不矛盾。[原始案例与局限](pcie-dispatch-wait.md)。

**5. 32路累计时，哪些可以相加**

对同一观测窗口T，应将所有占用/等待区间裁剪到窗口边界，并确保父子归属不重复：

```text
名额平均占用率 = 窗口内各名额持有时间之和 / (名额数 × T)
硬件平均忙碌率 = 各真实执行单元忙碌区间长度之和 / (单元数 × T)
平均等待线程数 = 所有线程等待区间长度之和 / T
```

同一执行单元的重复/重叠记录先合并，不能双计。名额占用率与硬件忙碌率是不同指标；bm-smi离散采样可作旁证，不能凭SDK墙钟倒推精确硬件busy。

例如在1秒观测窗口内，正确裁剪后的线程等待合计3秒，表示平均约3个线程在等，**不是主控或TPU利用率300%**。线程可以同时等待，也可以在一个资源执行时让另一个资源工作；全卡时间不能简单相加。

若要区分SDK调用内的CPU执行与不在CPU上运行的时间，可辅助记录线程CPU时钟，但墙钟减CPU时间仍混合了阻塞和可运行调度等待，不能单凭差值分配到某把锁。

**6. 怎样算这些等待造成多少业务损失**

等待账目先回答“发生在哪里、等多久、占着什么资源”。实际吞吐损失还要看它是否处于业务推进必须经过的路径，以及是否被其他并发工作覆盖。

```text
同配置优化吞吐增幅 = (优化后INF / 优化前INF - 1) × 100%
同时比较：最慢单路FPS、最长分析空窗、实际预览完成率、源滞后
```

消除单个样本的9.755 ms，不能宣布全系统吞吐提高74%或变成3.9倍；等待可能被其他线程覆盖，也可能转移到其他资源。已有反例：异步10FPS让总INF提高约17.3%，却产生47秒空窗；VPP限流把部分等待移到用户态，吞吐反而下降。

当前已测到应用调用频率、墙钟、部分完整驱动等待案例和独立控制读取。**尚缺按业务用途/通道与TID对齐、低扰动且稳定的资源持有与真实busy账目**。尤其VPP驱动记录覆盖SDK内部多类线程，不能把所有VPP根均值叫作单次预处理时间。后续按请求/取得/释放/完成记录分层累计，并保留无追踪对照，才能判断到底是硬件能力不足、资源占用被拉长，还是CPU调度/源帧过期造成供给中断。
