# PCIe 2.0 ×1：32 路分析、编码与视频墙实测

2026-09-23 已完成两张 Gen2 ×1 卡的并发、交换角色对照，共接受 20 个正式阶段。**设备内图像分析约 278–281 FPS，可以基本用满 TPU；当前 BGR 保存视频路径远慢于此。视频墙的严重掉速与本地视频落后后持续触发过期丢帧有关，单独关闭预览不能恢复。**

## 主要结果

两列按卡号排列，不按运行先后。每卡 32 路，各路独立打开同一份本地 1080p25 H.264 公路素材，YOLOv8s INT8 B1、score gate、64 KiB 合并、输出缓冲复用。所有数字为正式窗口数据。

| 路径 | device 0 总检测 FPS | device 1 总检测 FPS | TPU %（两卡分别） | 同期另一张卡的负载 |
|---|---:|---:|---|---|
| 不显示、不编码，device-bgr 逐帧分析 | 277.76 | 280.55 | 96.47 / 97.87 | 正常视频墙 |
| 保存带框视频，BGR + BM1684X 编码 | 12.00 | 13.29 | 4.93 / 5.00 | 正常视频墙 |
| 视频墙，250 ms 门槛 | 0.00 | 6.47 | 0.00 / 2.50 | 保存带框视频 |
| 视频墙，关闭过期门槛 | 192.85 | 195.37 | 70.30 / 71.27 | 正常视频墙 |
| 视频墙，250 ms 门槛、关闭预览 | 3.67 | 10.98 | 1.40 / 3.90 | 正常视频墙 |
| BGR 分析、不画框、不编码 | 13.69 | 24.79 | 7.80 / 8.56 | BGR 编码 |
| BGR 编码补充对照 | 5.50 | 11.90 | 4.17 / 4.00 | BGR 分析 |

不同表行的对卡负载不同，不能用跨行比值宣称某一个优化的严格收益。最后两行的交换复测使用 60 秒预热，其余一般为 30 秒；均测量约 60 秒。BGR 路径有明显波动，不能把 12–13 FPS 扩写为所有负载下的固定编码能力。

单独占用主机、仅 device 1 工作时，device-bgr 分析为 **279.85 FPS、最低单路 8.72 FPS、TPU 96.97%**，与双卡并发时的分析结果接近。

## 不做 HDMI 的含义

**仅分析并回传检测结果**：本次每路平均约 8.7 FPS，最低单路为 8.64 / 8.74 FPS，32 路都有结果。但入口采用逐帧顺序处理，不主动跳帧，测量末期最大播放计划落后约 58 秒。它验证了离线分析吞吐，不代表 32 路实时摄像头已经验收。每路 25 FPS 全帧分析需要总计 800 FPS，本次没有达到。

**不显示但保存带框视频**：当前入口走 BGR 图像路径，由主控处理图像及画框，调用 BM1684X VPU 编码。运行日志明确出现 `vpu_EncInit`、`sophon_idx` 和 `VPU core index 4`，没有使用 RK3588 MPP 或 CPU 软件编码。相比仅回传检测数字，此路径还涉及完整图像及编码处理，不能沿用约 280 FPS 的分析结论。

**仍运行视频墙，只关预览**：250 ms 过期门槛仍生效，本轮总检测仅 3.67 / 10.98 FPS，分别有 29 / 26 路正式窗口内零检测；去掉缩略图并没有解决崩塌。

## 过期策略对照说明了什么

同一配对交换卡号后：

| 配置 | device 0 | device 1 |
|---|---:|---:|
| 关闭过期门槛：总检测 FPS | 192.85 | 195.37 |
| 关闭过期门槛：最低单路 FPS | 5.85 | 5.95 |
| 关闭过期门槛：零检测通道 | 0 | 0 |
| 关闭过期门槛：解码 FPS | 591.82 | 597.10 |
| 关闭过期门槛：成功检测帧最大源年龄 | 22.65 秒 | 22.10 秒 |
| 正常门槛：总检测 FPS | 9.08 | 9.05 |
| 正常门槛：零检测通道 | 26 | 29 |
| 正常门槛：解码 FPS | 696.60 | 685.98 |

代码在解码后和送检前，根据本地文件帧的计划播放时刻 `frame->due` 判断过期。32×25 FPS 需要 800 解码 FPS，当前视频墙路径未达到；持续落后时，刚解出的帧也可能已经超过 250 ms，被丢弃而不进入推理。关闭门槛后所有路恢复检测、TPU 显著升高，支持该机制参与了崩塌。

但关闭门槛只是允许处理落后约 22 秒的图像，并没有恢复实时性。它还提高了实际送检负载，解码和预览受到更多竞争。根因不能简单写成“显示太慢”“PCIe 已满”或“某个驱动锁已证实”；解码为什么低于目标、SDK 调用中的执行与等待比例，还需要进一步分离。

## 图像路径与回传计数

设备内图像分析组的模型结果有效载荷约 29.39 / 29.71 MB/s；保存视频主对照的该项只有约 1.48 / 1.65 MB/s，却不代表整个 PCIe 下载或上传流量这么小。现有计数没有覆盖 BGR 图像桥接、编码图像/码流与协议开销。

1920×1080 BGR 一帧为 6,220,800 字节，远大于筛选后的检测数据。BGR 不编码对照仍然很慢，提示完整图像路径及其同步等待需要重点排查；但其对卡背景与 device-bgr 对照不同，不能仅凭本轮数据计算某个拷贝操作的独立成本。

单路编码烟测中，推理约 2.93 ms，解码调用约 53.84 ms、图像桥接约 19.73 ms、编码提交约 94.82 ms；32 路时这些调用及结果读取还有并发等待。因此“编码由 1684X 执行”不等于整条路径没有主控参与或图像往返，也不能把提交耗时当成编码硬件独占时间。

模型权重在实例初始化时加载，不会每帧重传；普通分析/编码入口每路一个进程，各自初始化模型实例。当前正式统计要求每路在预热结束前已完成首帧，启动未就绪的轮次被排除并复测。
