## 驱动内部分账：主要差距在等 VPP 名额

以下每行是“缩放请求均值＋类型转换请求均值”，两类请求分别统计；不是把不同线程墙钟当作硬件运行时间。父子项已去重。

| 两步合计，ms | 捕获 0 PCIe 2 | 捕获 0 PCIe 3 | 捕获 1 PCIe 2 | 捕获 1 PCIe 3 |
|---|---:|---:|---:|---:|

| CDMA 其余工作 | 0.104 | 0.070 | 0.105 | 0.070 |
| 描述符路径其余工作 | 0.217 | 0.475 | 0.335 | 0.450 |

| **总计** | **71.059** | **37.555** | **71.560** | **28.918** |

捕获 0 总差约 33.504 ms，等待名额差 33.586 ms；捕获 1 总差约 42.641 ms，等待名额差 42.642 ms。其余项相互抵消，因而等待差可以略大于总差。**在这些可核对样本中，差距几乎全部来自进入 VPP 前的名额等待，而不是卡内图像计算变慢三倍。**

`down_interruptible` 时间还包含名额授予后的调度唤醒，不能将其严格等同于纯硬件繁忙；完成等待同样包含硬件、通知和调度，不是纯执行时间。

历史那次“CDMA 锁等 9.755 ms”的单调用证明共享路径确实会阻塞，但本轮平均值远小于它，**不能继续用那个长尾案例代表当前平均预处理差距**。需区分“直接等待在哪里”和“什么工作延长名额占用、进而造成排队”。

## 排队负载账目新增了 OpenCV 解压

第一轮未追踪的 VPP 提交计数（仅完整落在 90 秒窗口内的调用）：

| 请求来源 | PCIe 2.0 次/秒 | PCIe 3.0 次/秒 |
|---|---:|---:|
| 显式两步预处理及预览 | 597.589 | 739.544 |
| 其他路径 | 767.544 | 768.000 |
| 合计 | **1365.133** | **1507.544** |

随后独立单路运行中保存了真实调用栈：

```text
VideoCapture::read / retrieve
→ cv::bmcv::decomp
→ bmcv_image_vpp_csc_matrix_convert
→ bm1684x_vpp_csc_matrix_convert
→ bm_trigger_vpp
```

这与已安装库反汇编中的 `decomp` 调用对应。厂商[OpenCV 公开实现](https://github.com/sophgo/sophon_opencv/blob/master/modules/videoio/src/cap_ffmpeg_impl.hpp)中，压缩布局解码帧在取出为 YUV 时需要展开；公开源码用于解释机制，不能冒充现场二进制的精确构建版本。现场调用栈和下一项配置日志才是实际运行依据。

因此，此应用的“硬件解码”不只是 VPU；返回应用之前还消耗 VPP。32×24=768 次/秒的这一步，先于 latest 筛选；以后被覆盖的帧已经做过解压。将解码完全视为不竞争 VPP 的独立阶段，会漏掉多数 VPP 请求。

两段采集中，PCIe 2.0 全部 VPP 请求取得名额后的累计驱动时间约 15.63 / 15.60 线程秒，相对于两个名额在 8 秒内共 16 名额秒已很接近上限。PCIe 3.0 对应 15.30 / 15.24 秒。此估计含取得名额前后的少量驱动工作，不是直接硬件利用率。

其中所有请求的 CDMA 锁调用累计：PCIe 2.0 为 2.888 / 2.802 秒，PCIe 3.0 为 1.166 / 1.111 秒。这些时间处于取得 VPP 名额之后，会延长名额占用。**单次较小的串行资源等待，可以通过接近饱和的名额队列放大为几十毫秒的调用等待。** 这与“336 B 描述符本身在线路上传了几十毫秒”不同。

## 两个 VPP 名额的资源预算核算

每秒两个名额合计约 2000 名额毫秒。在本场景中，解压背景请求约 `D=32×24=768/s`，每次检测另有两次预处理和平均 `p` 次预览。若取得名额后的平均驱动时间分别为 `S_D、S_1、S_2、S_P`，则近似需求约束为：

```text
D × S_D + FPS × (S_1 + S_2 + p × S_P) ≤ 2000 ms/s
FPS上界 ≈ (2000 − D × S_D) / (S_1 + S_2 + p × S_P)
```

捕获 0 的 PCIe 2.0：`S_D=1.5041 ms`，解码背景先消耗约 **1155.2 名额毫秒/秒**；两步预处理为 1.3340＋1.3761 ms，预览 1.5090 ms，实测 `p≈0.7380`。代入上界约 **220.95 FPS**，该捕获实际 **209.70 FPS**，低约 5.1%。第二捕获算得 **219.29**，实际 **208.12**，关系相近。

PCIe 3.0 相同算法上界 **289.74 / 292.26 FPS**，高于这个完整工作流约 272–278 FPS 的 TPU 吞吐区间，因此它更可能先受 TPU 约束。这里解释了为什么固定背景工作占据大量 VPP 预算时，PCIe 2.0 会先出现供给不足。

这不是独立测得的硬件极限预测：使用了当前负载下的服务时间和预览比例，名额边界还含少量驱动开销，内核追踪也有扰动。它是量纲正确的资源预算一致性核算，不能冒充用 PCIe 线速直接算出的理论 FPS。原始计算保存在 `verify_vpp_pool_model.py` 与 `vpp-pool-model.json`，明确保留全部假设及误差。
